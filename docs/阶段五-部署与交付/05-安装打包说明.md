## 一、交付物：一个发布包里必须有四样东西

只打 Python 包是不够的 —— 现场装的时候会缺东西。完整的发布包由四部分组成：

| 组成 | 目录 | 缺了会怎样 |
|---|---|---|
| ① 后端代码 | `app/` | 起不来 |
| ② 数据库脚本 | `scripts/` | 装完库里一家厂商都没有，控制台「厂商接入」是空的 |
| ③ 部署编排 | `deploy/` | 得现场手写 Dockerfile / compose / nginx |
| ④ 前端静态产物 | `admin-web/dist/` | nginx 挂到一个空目录，控制台白屏 |

外加：`docs/`（交付文档）、`dist-python/`（sdist + wheel）、`BUILD-INFO.txt`、`SHA256SUMS.txt`。

```bash
pip install -e ".[dev]"
```

## 三、一键打包（推荐）

```bash
# 在仓库根目录执行
python scripts/build_release.py
```

产物：

```
release/
├── llmbridge-1.0.0-<日期>/          ← 组装目录（可直接 scp 到服务器）
│   ├── app/                           后端源码
│   ├── scripts/                       初始化与迁移脚本
│   ├── deploy/                        部署产物
│   ├── admin-web/dist/                前端静态产物
│   ├── docs/                          交付文档
│   ├── dist-python/                   sdist + wheel
│   ├── BUILD-INFO.txt                 版本 / 构建时间 / git 提交 / 构建机
│   ├── SHA256SUMS.txt                 包内全部文件的 SHA256
│   ├── README.md  LICENSE  CHANGELOG.md
│   ├── .env.example  pyproject.toml  MANIFEST.in
│   └── .gitignore  .gitattributes
└── llmbridge-1.0.0-<日期>.zip       ← 分发包
```

### 可选参数

| 参数 | 作用 | 什么时候用 |
|---|---|---|
| `--skip-frontend` | 复用已有 `admin-web/dist/`，不跑 npm | 只改了后端。实测前端构建本身约 7 s，加 npm 启动开销共省约 15 s |
| `--skip-python` | 不重打 sdist / wheel | 只改了前端 |
| `--no-archive` | 只组装目录，不压 zip | 要直接 scp 目录时 |

完整一次（含前端构建 + Python 打包 + 组装 + 压缩）在本机约 **3 分钟**（其中 Python 的隔离构建环境占大半），产物约 **8.7 MB / 208 个文件**。

### 校验产物

```bash
# 逐文件校验完整性（传输后必做）
cd release/llmbridge-1.0.0-*        # 包名带构建日期，用通配即可
sha256sum -c SHA256SUMS.txt          # Linux
# Windows: Get-FileHash 逐项比对，或用 7-Zip 的 CRC 校验

# 目录树总览
cat BUILD-INFO.txt
```

## 四、分步打包（需要单独产出某一部分时）

### 4.1 后端：sdist + wheel

```bash
python -m build --sdist --wheel --outdir release/python-dist
```

产出：

| 文件 | 内容 | 用途 |
|---|---|---|
| `llmbridge-1.0.0.tar.gz` | 源码包，含 `app/` + `scripts/` + `deploy/` + LICENSE + README | 完整源码分发；`scripts/` 下的运维脚本只有它才有 |
| `llmbridge-1.0.0-py3-none-any.whl` | 纯 Python 轮子，只含 `app/` | 装进已有环境；不含 `scripts/`、`deploy/` |

> **sdist 与 wheel 的区别不是体积，是能力**：wheel 只含库本体，`scripts/` 不随它分发。
> 但**功能不受影响** —— 厂商目录预置的实现已在 `app/data/catalog_seed.py`（包内），
> 三个命令 `llmbridge-serve` / `llmbridge-seed` / `llmbridge-catalog` 在纯 wheel 下全部可用。
> 只有 `scripts/` 下的**额外运维脚本**（数据迁移等）需要 sdist 或 clone 仓库。
>
> 历史坑（已修）：早期版本把预置逻辑放在 `scripts/seed_provider_catalog.py`，
> wheel 装完 `llmbridge-catalog` 会以 exit 2 提示「找不到脚本」—— 界面因此一家厂商都没有。
> 实测对照见 §十二。

验证安装（在**干净**虚拟环境里验证，别在开发环境里自欺欺人）：

```bash
python -m venv /tmp/verify && source /tmp/verify/bin/activate   # Windows 用 .venv\Scripts\activate
pip install release/python-dist/llmbridge-1.0.0-py3-none-any.whl
python -c "import app.main; print('import ok')"
llmbridge-serve --help
```

### 4.2 前端：静态产物

```bash
cd admin-web
npm ci              # 用 ci 不用 install：锁文件是唯一真源，install 会改锁文件
npm run build       # = vue-tsc -b && vite build
```

产物 `admin-web/dist/`，含 `index.html` 与 `assets/`（带内容哈希的 js/css）。

- **`vue-tsc -b` 在 build 脚本里，类型错误会直接中断构建** —— 这是门禁，不要为了绕过它把
  `build` 脚本改成只跑 `vite build`。
- 前端请求全部使用**相对路径**（`/v1/...`、`/admin/...`），不写死后端地址。
  开发态由 `vite.config.ts` 的 proxy 转发，生产态由 nginx 同源代理 ——
  **切换环境不需要改任何业务代码，也不需要重新构建**。

### 4.3 Docker 镜像

系统有**两个**镜像：后端一个、前端一个。前端单独成像是为了支持「容器库形态」——
目标机不需要源码目录也能起完整系统。

```bash
# 后端。注意：上下文必须是仓库根目录（要拷 app/ 与 scripts/），Dockerfile 用 -f 指定
docker build -f deploy/Dockerfile -t llmbridge-api:1.0.0 .

# 前端。多阶段：node:22-alpine 里跑 npm ci + vue-tsc + vite build，
# 产物 dist 与 deploy/nginx.conf 一起进 nginx:1.27-alpine。
docker build -f deploy/Dockerfile.web -t llmbridge-web:1.0.0 .
```

导出为离线 tar（目标机不能拉取镜像仓库时用）：

```bash
docker save llmbridge-api:1.0.0 llmbridge-web:1.0.0 | gzip > llmbridge-images-1.0.0.tar.gz
# 目标机：docker load -i llmbridge-images-1.0.0.tar.gz
```

#### 推送到容器库（阿里云 ACR 等）

用 `deploy/publish-image.sh`，它把「提交前忘打标签 / 忘了加仓库前缀 / 只出一个架构」这几类
事故都堵在前面：

```bash
# 1) 先登录（密码由 docker 自己读，脚本与文件都碰不到）
docker login --username=<账号> registry.cn-hangzhou.aliyuncs.com

# 2) 构建并推送三个镜像（默认 registry.cn-hangzhou.aliyuncs.com/winyeahs，双架构）
bash deploy/publish-image.sh --tag 1.0.0

# 只交 x86 时显式单平台（跨架构构建走 QEMU，前端 npm ci + vue-tsc 尤其慢）
bash deploy/publish-image.sh --tag 1.0.0 --platform linux/amd64

# 只重推某一个（api / web / deploy）
bash deploy/publish-image.sh --tag 1.0.0 --only deploy

# 先看命令不执行
bash deploy/publish-image.sh --tag 1.0.0 --dry-run
```

三个镜像：`llmbridge-api`（后端，**内含安装脚本** `/opt/llmbridge/deploy/`）、
`llmbridge-web`（nginx + 内置 dist）、`llmbridge-deploy`（**纯安装器**：不含业务代码，
只有那一个脚本，约 8 MB）。

安装脚本为什么要放进镜像：脚本本身也得先送到目标机。默认取法是 Sub2API 同款
`curl -sSL https://raw.githubusercontent.com/dragonlin-ai/llmbridge/main/deploy/docker-deploy.sh | bash`
（KB 级、随 main 分支同步）；但国内访问 `raw.githubusercontent.com` 基本不可达，此时
**镜像载体**是等价退路 —— 容器库是目标机唯一一定能访问的地址（否则业务镜像也拉不下来），
而安装流程随后要拉的就是这套镜像，从 api 镜像里取脚本（`/opt/llmbridge/deploy/docker-deploy.sh`）
**不会多下载一个字节**、且全程零 GitHub：

```bash
docker run --rm --entrypoint cat <registry>/llmbridge-api:<tag> \
  /opt/llmbridge/deploy/docker-deploy.sh | bash -s --
```

`llmbridge-deploy` 是「只要脚本」的轻量替代，但它必须先在容器库里被设为**公开**
（阿里云 ACR 新建仓库默认私有：实测匿名令牌对 `llmbridge-api` / `llmbridge-web`
带 `pull` 权限，对新建的 `llmbridge-deploy` 为空 → 401），否则目标机得先 `docker login`。

> **国内构建器的坑（脚本已处理）**：`docker-container` 驱动的 BuildKit **不读宿主机的
> `daemon.json`**，所以「宿主机 `docker pull python:3.13-slim` 成功」并不代表构建能过 ——
> 它会死在拉基础镜像的元数据上，报
> `failed to authorize: ... auth.docker.io/token ... Bad Gateway`。
> 脚本会写一份 `~/.docker/buildx/llmbridge-buildkitd.toml` 给构建器指定 `docker.io`
> 加速器，配置变了就重建构建器（丢的只是构建缓存）。换加速器用环境变量：
> `LLMBRIDGE_REGISTRY_MIRRORS="https://a,https://b" bash deploy/publish-image.sh`。

产出（每个镜像两个标签）：

| 标签 | 性质 | 用途 |
|---|---|---|
| `1.0.0` | 浮动，可被后续推送覆盖 | 图省事时用 |
| `1.0.0-<git短sha>` | **不可变** | 生产锁版本；出问题能回到当时那一版 |

镜像名带完整仓库前缀（`registry.cn-hangzhou.aliyuncs.com/winyeahs/llmbridge-api:1.0.0`）——
**没有前缀的镜像 `docker push` 会直接报 `invalid reference format`**，所以本地 `docker build -t`
起的名字不能直接推。

两条与兼容性有关的固定选项，改之前请先读理由：

- `--provenance=false --sbom=false`：关掉 attestation。开着时 manifest list 里会多出
  `unknown/unknown` 平台条目，部分容器库与旧版 `docker pull` 会因此拒绝拉取。
- `--platform linux/amd64,linux/arm64`：buildx 多平台构建**只能 `--push`**，不能 `--load`
  到本机（单平台验证才用 `--load`）。

部署侧的用法见 [§6.1.1](#611-云端直拉形态推荐默认)。

## 五、打包相关文件逐个说明

这一节是**改动这些文件前必读**。每个文件都在解决一个具体的坑。

### 5.1 仓库根目录

| 文件 | 作用 | 关键点 / 改动注意 |
|---|---|---|
| `pyproject.toml` | 构建配置、依赖、CLI 入口、包发现 | `[tool.setuptools.packages.find] include=["app*"]` **依赖各子包存在 `__init__.py`**，缺了会静默漏包；`requires=["setuptools>=77"]` 是 PEP 639 许可证声明的门槛 |
| `MANIFEST.in` | 声明 **sdist** 内容 | 不写它，sdist 里就没有 `scripts/` 和 `deploy/`，拿到源码包的人无法完成部署。**wheel 不受此文件影响** |
| `.dockerignore` | 镜像构建上下文排除 | 排除 `.env`（镜像可被任何人拉取）、`node_modules`（几十万文件会拖垮构建）、`admin-web/dist`（由 nginx 容器 bind mount，不需要进后端镜像；`Dockerfile.web` 会在镜像内重新构建它）。**`**/tsconfig.tsbuildinfo` 不可省**：`vue-tsc -b` 会据此判定「已是最新」而跳过类型检查，宿主机残留一份就会让 `Dockerfile.web` 的类型门禁在镜像构建里静默失效 |
| `.gitattributes` | 换行符强制 | **`*.sh text eol=lf` 不可删**：Windows 上默认会把 `entrypoint.sh` 存成 CRLF，进 Linux 容器后报 `/bin/sh^M: not found`，镜像起来即崩。`*.ps1` 保持 CRLF |
| `.env.example` | 环境变量模板 | 标【生产必改】项严禁用默认值；含 compose 需要的 `POSTGRES_PASSWORD` / `HTTP_PORT`，以及容器库形态的 `LLMBRIDGE_REGISTRY` / `LLMBRIDGE_TAG` |
| `README.md` | 仓库门面 | sdist 构建时 setuptools 会读它作长描述，**缺失会导致 sdist 构建告警** |
| `LICENSE` | Apache-2.0 全文 | 与 `pyproject.toml` 的 `license = "Apache-2.0"` 必须一致 |
| `CHANGELOG.md` | 版本变更记录 | 可选；`build_release.py` 存在则打包，缺失仅告警 |
| `app/cli.py` | 命令行入口实现 | 见下 |
| `scripts/build_release.py` | 一键打包脚本 | 见下 |
| `scripts/verify_registry.py` | 容器库标签核验 | 走 Bearer 挑战查 `tags/list`，**不采信 `push` 的退出码**。默认只查必须公开的 api / web（`llmbridge-deploy` 默认私有，401 属预期）。只回显标签列表，从不打印令牌 |
| `scripts/verify_deploy.py` | 装后**功能性**核验 | 容器全 `healthy` 只说明进程活着。本脚本真打 HTTP：控制台 SPA、`/health`、`/admin/auth/login` 真实登录、厂商目录已铺、模型池留空、概览页不 500。内置 `ProxyHandler({})` 绕开本机代理（否则会把代理 502 误判成服务故障） |
| `scripts/check_compose_sync.py` | 内嵌副本一致性 | `docker-deploy.sh` 内嵌了一份 `docker-compose.image.yml`（供只有单文件的目标机离线用），于是同一内容存在**两份**。本脚本可不碰 Docker 独立比对，发布前自查用（脚本自身的运行期比对需要真的跑一次部署） |

### 5.2 `app/cli.py` —— 三条命令，每一条都在消灭一个高频故障

| 命令 | 实现 | 解决什么 |
|---|---|---|
| `llmbridge-serve` | 调 uvicorn，**强制传 `loop="app.core.eventloop:selector_loop_factory"`** | uvicorn 默认 loop 工厂在 Windows 返回 `ProactorEventLoop`，psycopg3 主动拒绝 → 「服务起来了、`/health` 200，但一访问数据库就 500」。这个坑不该让每个部署的人各踩一遍 |
| `llmbridge-seed` | 调 `app/services/bootstrap.run_first_run()` | 建表 + 默认管理员 + 内置评测样本 + 厂商接入目录，全部幂等。**与服务启动自动引导同源** —— 两条路径不会长出两种行为。注意 `loop_factory` 传**函数本身**，加括号会 TypeError |
| `llmbridge-catalog` | 调包内 `app/data/catalog_seed.py` 的 `seed_catalog()` | 预置厂商接入目录。**不再依赖 `scripts/` 定位**（那个探测逻辑 `_repo_root()` 已随实现搬进包内而删除），wheel 安装同样可用。默认只铺接入通道，`--with-models` 才连参考模型一起灌 |

### 5.2.1 `app/services/bootstrap.py` —— 首次运行引导（V1.2 新增）

「装完打开界面就该是能用的」这件事由它负责，四步全幂等、任一步失败只记 ERROR 不阻塞启动：

| 步骤 | 做什么 | 为什么必须在这 |
|---|---|---|
| `ensure_schema` | `create_all` 建表 | 表没建，登录接口直接 500，而后台日志是一串 `UndefinedTable`，看着像连接问题 |
| `ensure_admin` | 无管理员时建 `admin` / `admin123` | 没有管理员连登录页都过不去。建完打 WARNING 提示改密 |
| `ensure_eval_cases` | 无评测样本时写 4 条内置样本 | `eval_case` **没有任何新增接口**，不预置等于「评测看板」对普通使用者永久空白。模型真值留空，看板已正式支持该情形（`model_truth_cases`） |
| `ensure_providers` | 按目录版本预置接入通道 | 核心诉求：**13 家主流接入商一条不缺**。实测只跑旧的 seed 时库里只有 2 个开发用厂商 |

两个设计点值得记住：

- **用标记判重，不用「表为空」**。`sys_config.catalog_seed_version` 记录已预置到的目录版本：
  使用者把目录清空了，重启不会被「复活」；目录升级（版本号变化）才重新预置 ——
  于是老装机也能拿到新增的厂商通道。
- **多 worker 并发靠唯一约束兜底**。`provider.name` / `admin_user.username` 都有唯一约束，
  多个 worker 同时启动时后者会撞约束 —— 那不是故障，回滚并记为「已由其他进程完成」。
- 整体开关 `AUTO_BOOTSTRAP`（默认 `true`）。生产由 DBA 管库时置 `false`，改由运维跑 `llmbridge-seed`。

`python -m app.cli {serve|seed|catalog}` 是兜底入口，console script 不在 PATH 时可用。
**不要用 `python app/cli.py`** —— 那样 `sys.path[0]` 是 `app/` 而非仓库根，连
`import app.core.eventloop` 都会失败。

### 5.3 `scripts/build_release.py`

| 行为 | 说明 |
|---|---|
| 前端构建失败即终止 | 刻意不做静默降级：产出「缺 `dist/`」的包，现场才暴露，排查成本远高于重打一次 |
| 用 `npm ci` 而非 `npm install` | `install` 会顺手改 `package-lock.json`，导致「打出来的依赖」与「提交记录」不一致 |
| 校验 `dist/index.html` 存在 | 只看 npm 退出码不够：构建"成功"但产物为空目录是可能的 |
| Windows 上经 `cmd.exe /c` 执行 npm | `CreateProcess` 不能直接执行 `.cmd`，直接调 `npm.cmd` 会失败 |
| 生成 `SHA256SUMS.txt` | 覆盖包内全部文件（不含清单自身），交付后可逐项校验传输完整性 |
| 生成 `BUILD-INFO.txt` | 排障第一个要看的就是「这个包是什么时候、哪个提交打的」 |
| **要用项目 venv 跑** | `python -m build` 需要 `build` 包（外加 `setuptools>=77` / `wheel`）。用系统 Python 或其它解释器会以 `No module named build` 直接失败。→ `.\.venv\Scripts\python.exe scripts\build_release.py`。**脚本目前没做这项前置检查**，报错形态是原生 Python 异常，不像「缺依赖」那么友好（待改进） |

### 5.4 `deploy/` 目录

| 文件 | 作用 | 关键点 |
|---|---|---|
| `install.sh` | **方式一：Linux 一键安装（推荐）** | 一条 `curl` 完成：拉源码 → 建运行用户 → venv+依赖 → 生成 `.env`（随机密钥）→ 引导 → **自动装 Node.js 并构建前端** → **自动装并配好 Nginx** → 注册 systemd → **打印控制台地址**。Node.js 这一环同样做到「装完即用」：缺 Node 或版本 < 20 时先试发行版仓库，不够就下官方预编译包（先 `nodejs.org`、不通走 `npmmirror`）装进 `/usr/local/lib/nodejs`，**不覆盖包管理器的既有文件**，`PATH` 前置避免 npm 被旧 node 带跑；npm 源首次失败会用 `registry.npmmirror.com` 自动重试。Nginx 这一环：没装就按 `apt`/`dnf`/`yum`/`zypper`/`apk` 自动装；渲染并写入站点配置；**移走发行版自带默认站点**（否则它的 `default_server` 会把请求接走 → 访问到的是欢迎页）；按需 `setsebool -P httpd_can_network_connect 1` 并放行防火墙端口；探活成功才对外给地址。`--no-nginx` / `--no-node-install` 可分别跳过这两环（改用自备的）。**幂等：重跑即升级，且绝不覆盖既有 `.env`**（一旦覆盖，`ENCRYPTION_MASTER_KEY` 变了，已存厂商密钥全部解不开）。DB 默认策略是探测本机 `5432`：通则 PG、不通则 SQLite，保证装完就能打开界面。支持 `--uninstall/--purge/--frontend-only/--no-service/--node-version/--node-mirror/--npm-registry` 等 |
| `docker-deploy.sh` | **方式二：Docker Compose 一键部署（推荐）** | **默认云端直拉形态**：不需要源码、不需要本地构建，只取编排文件 + `compose pull` + `up -d`（目标机只要有 Docker 且能访问容器库，见 §6.1.1）。加 `--source` 则为本地源码构建形态：拉源码 → 生成 `.env` → **用 `node:22-alpine` 容器构建前端**（宿主机无需 Node.js）→ `compose up -d --build` → 轮询 `/health`。子命令 `status/logs/down/purge/upgrade`。`logs`/`down` 等运维子命令**不允许联网下载**（部署目录被删时不会莫名开始拉源码） |
| `publish-image.sh` | **容器库形态的发布侧** | 用 `buildx` 构建并推送 api + web + deploy **三个镜像**（`--only` 可只发其一）。每个镜像打两个标签：浮动 `1.0.0` 与不可变 `1.0.0-<git短sha>`。固定带 `--provenance=false --sbom=false`（避免 manifest list 出现 `unknown/unknown` 条目导致部分容器库拉不下来）。**凭据只走 `docker login` 或 `REGISTRY_USER`/`REGISTRY_PASSWORD` 环境变量，脚本里绝不落盘**。`--dry-run` 不依赖 Docker 守护进程（没开 Docker 也能先看一眼会推什么） |
| `Dockerfile.web` | 前端镜像 | 阶段一 `node:22-alpine` 里 `npm ci` + `vue-tsc -b && vite build`（**类型检查刻意不跳过**），阶段二 `nginx:1.27-alpine` 内置 dist 与 `nginx.conf`。**改了 nginx.conf 必须重建这个镜像**（想临时覆盖可挂载） |
| `apple-container.sh` | **方式三：macOS Apple container** | 子命令 `init/up/status/logs/shell/restart/down/purge/upgrade`。默认**单容器 + SQLite**：Apple container 是逐容器 CLI，没有 compose 的依赖编排与健康等待，让它管 PG+Redis+应用三层就得自己写启动轮询，脆弱难排障 —— 完整形态请走方式二 |
| `nginx-standalone.conf` | 裸机形态的站点配置**模板** | 三个占位符 `__API_PORT__` / `__LISTEN_PORT__` / `__DIST_DIR__` 由 `install.sh` 用 sed 替换后输出为 `nginx-llmbridge.conf`，**再自动装进 `/etc/nginx/conf.d/llmbridge.conf`**（`nginx-llmbridge.conf` 是生成物、不在仓库里，所以别去仓库里找它）。与 `nginx.conf` 同源，同样带 SSE 必需的四件套（`proxy_buffering off` 等） |
| `Dockerfile` | 后端镜像 | 仍推荐 **`pip install -e .`**（改代码免重装、`scripts/` 运维脚本可用），但**不再是功能必需**：厂商目录预置已进包内，非可编辑安装也不会丢功能。以非 root 用户运行；健康检查用标准库脚本，不装 curl |
| `docker-compose.yml` | 编排 api / db / redis / nginx（源码形态） | `DATABASE_URL` 用 `postgresql+psycopg://...@db:5432` 覆盖 `.env` 里的 127.0.0.1；`POSTGRES_PASSWORD` 用 `:?` 语法强制必填，没设直接起不来而不是静默用弱密码。前端 `dist` 靠 **bind mount** 进 nginx，所以改前端必须重新 build |
| `docker-compose.image.yml` | 编排 api / db / redis / web（容器库形态） | **没有任何 `build:` 段**，四个服务全部从容器库拉取，前端 dist 与 nginx.conf 都在 `llmbridge-web` 镜像里，因此**零 volumes、零源码依赖**。镜像名用 `${LLMBRIDGE_REGISTRY:-默认}` / `${LLMBRIDGE_TAG:-1.0.0}` 插值。与 `docker-compose.yml` **共用 project name 与数据卷**，所以换形态不会丢数据；但服务名不同（`nginx` ↔ `web`），切换前必须先 `down`，否则留下孤儿容器 |
| `nginx.conf` | 反向代理 | **`proxy_buffering off` 是最不能删的一行**：开着它 SSE 会被缓冲到整段结束才下发，现象是「流式一直转圈、最后一次性刷出来」，而 curl 直打 8000 完全正常。`/admin/` **刻意不关** buffering（无流式需求，关了只降吞吐）。容器库形态下这份文件被**内置进 `llmbridge-web` 镜像**，改它要重建镜像 |
| `entrypoint.sh` | 容器入口 | 只跑一次 `llmbridge-seed`（失败仅告警，不阻断启动）再 `exec` 服务。**已去掉单独的 `llmbridge-catalog` 一步** —— seed 现在已包含厂商目录预置，且启动引导会再兜一次。留着它的价值只是让容器日志里**先**出现初始化输出，而不是混在 uvicorn 日志里 |
| `healthcheck.py` | 容器探活 | 只用标准库；显式 `ProxyHandler({})` 绕开宿主/容器代理，否则本地探活会被代理拦成 502，把「服务正常」误判成不健康 |
| `linux/llmbridge.service` | systemd 单元 | **刻意不用 `EnvironmentFile`**：systemd 的 dotenv 方言与 pydantic-settings 不一致（引号、行内 `#` 截断），同一份 `.env` 被两套解析器读会造成「配置值≠生效值」。让应用自己读 `.env` 是唯一真源。已带 `NoNewPrivileges` / `ProtectSystem=full` 等加固。`install.sh` 从这份模板 sed 生成实际单元（替换路径与端口/用户），**保证模板与线上单元同源** |
| `windows/start-backend.ps1` | Windows 启动后端 | 优先调 `llmbridge-serve`；回退裸 uvicorn 时也会补 `--loop`。输出健康检查地址 |
| `windows/start-dev.ps1` | Windows 开发一键启动 | 后端开独立窗口 + vite 前台。**`--host 127.0.0.1` 不可省**：vite 默认只绑 IPv6 的 localhost，IPv4 访问会「连接被拒」 |

## 六、安装

### 6.0 一键脚本（推荐先看这里）

仓库自带三个脚本，覆盖三种部署形态。它们与 6.1~6.4 的手工步骤做的是**同一件事**，
区别是「不用记命令、不用手写密钥、不会漏掉前端构建」。

| 方式 | 命令 | 适用 |
|---|---|---|
| 一 · 脚本安装 | `curl -sSL https://raw.githubusercontent.com/dragonlin-ai/llmbridge/main/deploy/install.sh \| sudo bash` | Linux 裸机（systemd） |
| 二 · Docker Compose（云端直拉，推荐） | `curl -sSL https://raw.githubusercontent.com/dragonlin-ai/llmbridge/main/deploy/docker-deploy.sh \| bash` | **交付给客户 / 生产首选**：目标机只要有 Docker，不需要源码、不需要本地构建（见 §6.1.1）。默认只生成 `./docker-compose.yml` + `./.env`，再用标准 `docker compose up -d` 启停；末尾加 `deploy` 一键全量。GitHub 不可达时改用镜像取脚本（同样写在 §6.1.1） |
| └ 二 · 本地源码构建（可选） | `bash deploy/docker-deploy.sh --source` | 你持有源码、想改代码后再构建（见 §6.1） |
| 三 · Apple container | `./deploy/apple-container.sh init` 然后 `./deploy/apple-container.sh up` | macOS 26+ / Apple Silicon |

> **国内网络注意**：方式一与方式三都要能访问 `github.com`（下载脚本或源码）；
> **方式二默认那条 curl 取脚本同样要访问 `raw.githubusercontent.com`**（KB 级一次请求）。
> 国内访问不了 GitHub 时，方式二换成 §6.1.1 里的**镜像取脚本**写法即可 —— 安装脚本随
> `llmbridge-api` 镜像从容器库取（零 GitHub 请求），编排文件内嵌在脚本里，目标机只需
> 能访问容器库（默认阿里云 ACR，可用 `--registry` 换成任意第三方镜像库）。

另有一个**发布侧**脚本 `deploy/publish-image.sh`（构建 api + web + deploy 三个镜像并推送到
容器库），它不做部署，用法见 §4.3。

四个共同的设计约束：

- **幂等**：重复执行等于升级，`.env`、数据库、已录入的厂商密钥**一律不动**。
  这不只是「方便」—— `.env` 里的 `ENCRYPTION_MASTER_KEY` 一旦被覆盖，已存密钥就全部解不开。
- **密钥自动生成**：`JWT_SECRET`、`ENCRYPTION_MASTER_KEY`（compose 形态再加 `POSTGRES_PASSWORD`）
  用随机值生成写入 `.env`，权限 `600`。
- **前端不漏**：控制台是独立 SPA，后端**不托管**静态文件。方式一/二都会构建 `admin-web/dist`。
  **漏掉构建的现象是「服务正常、浏览器一片空白」**，所以脚本要么构建、要么明确告警并给出
  补装命令（`--frontend-only`），绝不静默跳过。
- **Node.js 不漏**：方式一**不再把「装 Node.js」留给用户** —— 缺失或版本 < 20 时自动装：
  先试发行版仓库（最快、走本地源，Alpine 只能走这条），版本不够就下载官方预编译包
  （先 `nodejs.org`、不通再走 `npmmirror` 镜像），解压到 `/usr/local/lib/nodejs` 并软链到
  `/usr/local/bin`，**已存在的同名实体文件绝不覆盖**。构建时把新目录前置进 `PATH`：
  npm 的 shebang 是 `#!/usr/bin/env node`，若旧的 node 仍排在前面，npm 会拿旧 node 去跑新 npm，
  报的却是一堆语法错 —— 现象与成因相隔极远。`--no-node-install` / `--node-version` /
  `--node-mirror` / `--npm-registry` 可分别接管这四件事。
- **Nginx 不漏**：方式一**不再把「装 Nginx / 配站点 / 放行端口」留给用户** —— 这三步都在脚本内
  完成，结束时直接打印 `控制台地址 http://<服务器IP>/`。之所以做这个改动：实测「把三条命令甩给
  用户」会卡在最不必要的地方 —— 没装 Nginx 时照抄 `cp` 只得到
  `cp: 无法创建普通文件 '…': 没有那个文件或目录`，而这句报错字面像在怪站点配置，
  真实成因却是**目标目录不存在**，很容易被带着排查错方向。
- **提示语里的命令必须自包含**：脚本用 `self_cmd()` 生成「补构建」命令，优先指向
  `<安装目录>/deploy/install.sh`。**不能直接用 `$0`** —— 通过 `curl … | sudo bash` 执行时
  `$0` 就是字符串 `bash`，拼出来的 `sudo bash bash --frontend-only` 照抄必挂。
- **不谎报就绪**：`打印的地址`、`控制台已就绪` 这两处只在探活通过（且前端确实构建成功）时才出现。
  站点通了但前端没构建时，脚本明说「页面暂时空白」而不是打印「已就绪」——否则用户按提示打开
  只会看到白页，反而更怀疑是系统坏了。
- **改 `.env` 必须重启**：`systemctl restart llmbridge` / `docker compose restart api`。
  配置在进程启动时读取，改了不重启不生效。

> **验证边界（如实标注）**：方式一与方式三的脚本**未在真实 Linux / macOS 机器上端到端执行过**
> （开发机是 Windows，且本机 Docker 守护进程未启动，无法用容器代替）。
> 已完成的验证是：`bash -n` 语法检查、shellcheck（`-S warning`）零告警、
> 模板占位符与 `install.sh` 中 sed 替换的交叉核验、依赖文件（systemd 单元 / Dockerfile /
> compose / package-lock.json / entrypoint）存在性核验。
>
> **「自动装并配置 Nginx」这一环额外做了函数级自测**：把脚本末尾的 `main` 调用去掉后 `source`
> 进测试桩，逐项验证 `ensure_nginx` 的四个分支 —— 站点配置未就绪 → 早退；`--no-nginx` → 跳过；
> 无可用包管理器 → 告警且**返回 0 不阻断安装**；已就绪 → 打印地址。并验证 `print_summary` 在
> 「已就绪 / 已就绪但前端未构建 / 未就绪」三种状态下的输出，以及 `nginx_disable_default_sites`、
> `nginx_fix_selinux`、`nginx_open_firewall`、`nginx_start_or_reload` 在目标文件/命令缺失时
> **什么都不做且返回 0**（不会误伤宿主机）。
>
> **「自动装 Node.js 并构建前端」这一环同样做了函数级自测**（`ensure_node` 全链路 37 项断言，
> 分 A/B 两段独立进程执行）：PATH 无/有 node 的判定；`--no-node-install` 返回 1 而非假成功；
> 包管理器失败 → 回退官方预编译包；**官方源不通自动换国内镜像**且拼出的 URL 形态正确；
> 解压出的 node 可执行、`PATH` 确实被前置；未知 CPU 架构 / 无 `curl`、`wget` 时优雅返回 1；
> 构建成功时置位 `FRONTEND_OK` 并产出 `dist/index.html`；**Node 装不上时不阻断安装（返回 0）、
> 不谎报就绪**；`self_cmd()` 在 `$0=bash`（管道执行）下仍给出可照抄的命令；
> `print_summary` 四种状态下的措辞与实际打印的小节一致、且**绝不谎报「控制台已就绪」**。
> 下载与包管理器用桩替换，`NODE_INSTALL_ROOT` / `NODE_LINK_DIR` 指到临时目录，**未碰宿主机**。
> 其中一项是真抓到缺陷的：本机 `ln -s` 会**静默**产出 0 字节空文件（退出码仍是 0），
> 原先只判断 `ln` 的退出码，等于把「软链没建起来」这件事完全静默掉 —— 已改为 **`ln` 之后
> 再验链接可执行**，失败即告警（但仍继续，因为构建走绝对路径不依赖它）。
> **仍未在装有 systemd 与 Nginx 的真实机器上跑过**，首次使用请留意脚本输出。

### 6.1 Docker Compose · 本地源码构建（形态 A，可选）

> **推荐默认形态是 [§6.1.1](#611-云端直拉形态推荐默认) 的云端直拉** ——
> 一条命令、不需要源码、不需要本地构建（默认 curl 取一次脚本，GitHub 不可达有镜像退路）。
> 本节是「你本地已有源码、想改代码后再构建」
> 时使用的本地源码构建形态（加 `--source` 走这条）。

```bash
# 1) 解包
unzip llmbridge-1.0.0-<日期>.zip && cd llmbridge-1.0.0-<日期>

# 2) 配置
cp .env.example .env
#    必改三项：
#      JWT_SECRET             → python -c "import secrets;print(secrets.token_urlsafe(32))"
#      ENCRYPTION_MASTER_KEY  → openssl rand -base64 32
#      POSTGRES_PASSWORD      → 任意强口令（compose 会用它初始化 db 并注入 api）
#    生产另需确认 ALLOW_LOCAL_BASE_URL=false

# 3) 起
docker compose --env-file ./.env -f deploy/docker-compose.yml up -d --build
```

> ⚠️ `--env-file ./.env` **不能省**：`-f` 指到 `deploy/` 后，compose 只在**编排文件所在目录**
> 找 `.env` 做变量插值（`docker-compose.yml` 里的 `env_file: ../.env` 只管容器内环境变量），
> 缺了就报 `required variable POSTGRES_PASSWORD is missing a value`。

首次启动会自动建表、灌厂商目录，再拉起 4 个 worker。

```bash
# 4) 验证
curl -f http://localhost/health                                  # {"status":"ok"}
curl -s http://localhost/admin/providers -H "Authorization: Bearer <token>" | head -c 400
# 拿 token：
curl -s -X POST http://localhost/admin/auth/login \
     -H 'Content-Type: application/json' \
     -d '{"username":"admin","password":"admin123"}'
```

> **改了前端（即使没改后端）必须 `--build` 吗？**
> 不必。`admin-web/dist` 是 bind mount 进 nginx 容器的，重新构建前端 + `docker compose restart nginx`
> 即可。但**改后端代码必须 `--build`**，否则跑的还是旧镜像层。

### 6.1.1 云端直拉形态（推荐默认）

适用场景：交付给客户、目标机不方便放源码、多台机器要跑同一版本 —— 也是方式二的**默认形态**。
**脚本默认动作（子命令 `prepare`，可省）只生成配置、不碰 Docker；命令末尾加 `deploy`
才连启动一起做完。**
发布侧怎么把镜像推进容器库，见 [§4.3](#43-docker-镜像)。默认镜像库是阿里云 ACR
（`registry.cn-hangzhou.aliyuncs.com/winyeahs`），可用 `--registry <host>/<命名空间>` 换成任意第三方镜像库。

**目标机四步**（前提：装了 Docker + Compose v2，且容器库可达；第 2 步需能访问
GitHub raw —— 不可达时用紧随其后的镜像退路，同样写在这里）：

```bash
# 1. 创建部署目录
mkdir -p llmbridge && cd llmbridge

# 2. 准备：只生成 ./docker-compose.yml + ./.env，全程不碰 Docker
curl -sSL https://raw.githubusercontent.com/dragonlin-ai/llmbridge/main/deploy/docker-deploy.sh | bash -s --

#    GitHub（raw）不可达时的等价取法 —— 从容器库的 api 镜像取（零 GitHub，
#    且安装随后拉的就是这套镜像，取脚本不会多下载一个字节）：
#    docker run --rm --entrypoint cat \
#      registry.cn-hangzhou.aliyuncs.com/winyeahs/llmbridge-api:1.0.0 \
#      /opt/llmbridge/deploy/docker-deploy.sh | bash -s --

# 3. 启动（首次自动拉取镜像）
docker compose up -d

# 4. 跟随后端日志
docker compose logs -f api
```

`prepare`（第 2 步）会自动走完：写根目录编排 `./docker-compose.yml`（真源
`deploy/docker-compose.image.yml` 的副本，唯一差异是 `env_file` 由 `../.env` 改写为
同目录 `.env`）→ 生成 `.env`（随机 `JWT_SECRET` / `ENCRYPTION_MASTER_KEY` /
`POSTGRES_PASSWORD`，并写入 `LLMBRIDGE_REGISTRY` / `LLMBRIDGE_TAG`）→ 打印下一步命令。
**它不调用 Docker** —— 前置条件里的 Docker 是给第 3 步用的。

**连启动一起做完**：第 2 步末尾加 `deploy`（生成配置 → `compose pull` → `compose up -d`
→ 轮询 `/health` → 打印控制台地址与默认账号；幂等，可重复执行）。

常用变体与后续运维（把取脚本那条管道记成一个变量；GitHub 不可达时把 `$LB` 换成
镜像取法那条 `docker run --rm --entrypoint cat …` 管道即可）：

```bash
LB='curl -sSL https://raw.githubusercontent.com/dragonlin-ai/llmbridge/main/deploy/docker-deploy.sh'

$LB | bash -s -- --port 8080          # 生成时换控制台端口（写进 ./.env）
$LB | bash -s -- --tag 1.0.0-<sha>    # 锁不可变标签（写进 ./.env 的 LLMBRIDGE_TAG）
$LB | bash -s -- deploy               # 配置 + 启动一条龙
$LB > docker-deploy.sh                # 只落盘，先审阅再跑（bash docker-deploy.sh 同效）

# 之后的启停用标准 compose（同一目录执行，无需再调脚本）：
docker compose ps                      # 状态 + 健康检查
docker compose logs -f api             # 跟随日志
docker compose down                    # 停止（保留数据卷）
```

`status` / `logs` / `down` / `upgrade` / `purge` 脚本子命令仍然保留：在 prepare 布局的
目录里会自动识别 `./docker-compose.yml`，与上面的标准 compose 命令等价。

在源码仓库内（自家运维）等价写法：

```bash
bash deploy/docker-deploy.sh           # prepare：生成配置
bash deploy/docker-deploy.sh deploy    # 一条龙
```

> **取脚本的两个载体（等价，默认 curl）**：默认与 Sub2API 同款 ——
> `curl -sSL …/deploy/docker-deploy.sh | bash`（KB 级一次请求、随 main 分支同步，
> 与方式一 install.sh 同一取法）。`raw.githubusercontent.com` 在国内不可达时，
> 改从容器库的 **api 镜像**里取（`/opt/llmbridge/deploy/docker-deploy.sh`）：容器库是
> 目标机唯一一定能访问的地址（否则业务镜像也拉不下来），安装流程随后要拉的就是这套镜像，
> **取脚本这一步不会多下载一个字节**。镜像取法的 `--entrypoint cat` 不能省 ——
> api 镜像默认入口会先做数据库初始化再起服务。
>
> **更轻的可选写法**：另有 8 MB 的纯安装器镜像 `llmbridge-deploy`（只打印脚本）。
> 它要求该仓库在容器库里被设为**公开** —— 阿里云 ACR 新建仓库默认私有，匿名令牌不带
> pull 权限，直接 401（实测：`llmbridge-api` / `llmbridge-web` 可匿名拉取，
> 新建的 `llmbridge-deploy` 不可）。控制台「容器镜像服务 → 命名空间 → 仓库 → 修改」
> 设为公开后可用：
>
> ```bash
> docker run --rm registry.cn-hangzhou.aliyuncs.com/winyeahs/llmbridge-deploy:1.0.0 \
>   | bash -s --
> ```
>
> 私有容器库：任一写法都可以传 `REGISTRY_USER` / `REGISTRY_PASSWORD` 环境变量，
> 脚本会在 `pull` 前自动 `docker login`（`--password-stdin`，凭据不落盘、不进 `.env`）。

脚本动作（默认 `prepare`）：写内嵌的根目录编排（**脚本自带，不联网下载**）→
生成 `.env` → 打印 `docker compose up -d` 等下一步；加 `deploy` 时续跑
`compose pull` → `compose up -d` → 轮询 `/health`。

部署目录最终**只有两样东西**：

```
llmbridge/
├── docker-compose.yml
└── .env
```

（上一版脚本的旧布局 `llmbridge/deploy/docker-compose.image.yml` 仍会被自动识别；
在旧目录里重跑会沿用既有 `.env`，不会分叉出新库。）

手工等价操作（在部署目录下执行 —— 根形态编排不需要 `-f` / `--env-file`）：

```bash
docker compose pull
docker compose up -d
```

> 只有**旧布局 / 仓库内**的 `deploy/docker-compose.image.yml` 才需要显式指定：
> `docker compose --env-file ./.env -f deploy/docker-compose.image.yml up -d`
> —— `--env-file` 不能省：变量插值只读**编排文件所在目录**的 `.env`，默认会去找
> `deploy/.env`，缺了报 `POSTGRES_PASSWORD is missing a value`。
> 根形态副本已把 `env_file` 改写为同目录 `.env`，两条路径落在同一份文件上。

**与本地源码构建形态的差异对照**：

| 对比项 | 本地源码构建形态（`--source`） | 云端直拉形态（默认） |
|---|---|---|
| 目标机需要源码 | 需要（或脚本下载） | **不需要** |
| 目标机需要 GitHub | 需要（下载脚本 / 源码） | **不需要**（脚本与编排都来自容器库） |
| 前端 `dist` | bind mount，必须本地构建 | 在 `llmbridge-web` 镜像内 |
| `nginx.conf` | 挂载仓库内文件 | 在 `llmbridge-web` 镜像内 |
| 升级方式 | `git pull` + `up -d --build` | 改 `LLMBRIDGE_TAG` + `pull` + `up -d` |
| 改前端之后 | 重新 build dist + restart nginx | 重新发布镜像 + `pull` |
| 数据卷 | `llmbridge_pgdata` / `llmbridge_redisdata` | 同左（两种形态共用） |

**两种形态之间切换**：共用 project name `llmbridge` 与同一套数据卷，所以换形态不丢数据；
但服务名不同（本地源码构建形态是 `nginx`，云端直拉形态是 `web`），**必须先 `down` 再 `up`**：

```bash
docker compose --env-file ./.env -f deploy/docker-compose.yml down       # 从本地源码构建形态切走之前
docker compose --env-file ./.env -f deploy/docker-compose.image.yml up -d
```

**升级与回滚**（数据卷不动，所以回滚不需要动数据库）：

```bash
# 升级
sed -i 's/^LLMBRIDGE_TAG=.*/LLMBRIDGE_TAG=1.0.1/' .env
docker compose pull
docker compose up -d

# 回滚：把 LLMBRIDGE_TAG 改回上一版（建议写成不可变标签 1.0.0-<git短sha>），重跑上面两行
# 旧布局 / 仓库内目录：两条 compose 命令换成
#   docker compose --env-file ./.env -f deploy/docker-compose.image.yml pull / up -d
```

**常见问题**：

- `pull` 报 manifest 不存在 —— tag 没发布成功，或目标机架构不在镜像的平台列表里。
  用 `docker manifest inspect registry.cn-hangzhou.aliyuncs.com/winyeahs/llmbridge-api:1.0.0` 核对。
- 控制台 404 / 空白 —— 容器库形态不可能「忘了构建前端」（dist 在镜像里），
  先确认 `web` 容器真的起来了。
- `exec format error` —— 镜像架构与本机不符（如 arm64 镜像跑在 x86）。重新发布时
  带上目标平台。
- **Windows 的 Git Bash 里报 `cat: 'C:/Program Files/Git/opt/...': No such file or directory`**
  —— 不是镜像的问题，是 MSYS 把 `/opt/llmbridge/...` 这个**容器内路径**当成本机路径改写掉了。
  前面加 `MSYS_NO_PATHCONV=1` 即可：`MSYS_NO_PATHCONV=1 docker run --rm --entrypoint cat …`。
  Linux / macOS 上没有这一层，PowerShell / cmd 也不受影响。

### 6.2 Linux 裸机（systemd）

> 已用 `deploy/install.sh` 装过的可以跳过本节 —— 下面是**等价的手工步骤**，
> 用来理解脚本到底做了什么，或在脚本不适用时（不用 systemd、走离线发布包）照着做。

```bash
# 1) 部署目录与专用账号
sudo useradd --system --home /opt/llmbridge --shell /usr/sbin/nologin llmbridge
sudo mkdir -p /opt/llmbridge && sudo chown -R llmbridge:llmbridge /opt/llmbridge

# 2) 放代码（解包后的发布包目录内容）
sudo -u llmbridge cp -r /tmp/llmbridge-1.0.0-<日期>/. /opt/llmbridge/
cd /opt/llmbridge

# 3) 虚拟环境与依赖
sudo -u llmbridge python3 -m venv .venv
sudo -u llmbridge .venv/bin/pip install -e .

# 4) 配置
sudo -u llmbridge cp .env.example .env
sudo -u llmbridge vi .env          # 改 JWT_SECRET / ENCRYPTION_MASTER_KEY / DATABASE_URL

# 5) 初始化（幂等；其实跳过也行——启动引导会自动做同样的事）
sudo -u llmbridge .venv/bin/llmbridge-seed

# 6) 注册服务
sudo cp deploy/linux/llmbridge.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now llmbridge
sudo systemctl status llmbridge
journalctl -u llmbridge -f
```

> **用方式一（`install.sh`）时，下面这几段可以跳过** —— 装 Nginx、渲染并写入站点配置、
> 移走发行版自带默认站点、放行 SELinux 与防火墙，脚本都已自动做完，结束时还会打印控制台地址。
> 本节保留给**手工安装**或**自备 web 服务器**（`--no-nginx`）的场景。

前端静态产物交给 nginx。**直接用现成模板**：`deploy/nginx-standalone.conf` 就是为这个场景写的，
占位符替换后即可用（等价于手工把 `root` 指向 `/opt/llmbridge/admin-web/dist`、
`upstream` 改成 `127.0.0.1:8000`）：

```bash
cd /opt/llmbridge
sudo sed -e 's#__API_PORT__#8000#g' -e 's#__LISTEN_PORT__#80#g' \
         -e 's#__DIST_DIR__#/opt/llmbridge/admin-web/dist#g' \
         deploy/nginx-standalone.conf | sudo tee /etc/nginx/conf.d/llmbridge.conf >/dev/null
sudo nginx -t && sudo systemctl reload nginx
```

> **前提是本机已装 Nginx**。没装时 `/etc/nginx/` 整个不存在，上面这条 `tee`（或
> `install.sh` 结尾提示的 `cp`）会失败并报
> `无法创建普通文件 '/etc/nginx/conf.d/llmbridge.conf': 没有那个文件或目录` ——
> **这句报错说的是目标目录缺失，不是站点配置有问题**（源文件缺失时报的是「无法获取 … 的状态」）。
> 先装好再回来跑：
>
> ```bash
> sudo dnf install -y nginx       # RHEL / CentOS / Fedora
> sudo apt-get install -y nginx   # Debian / Ubuntu
> sudo systemctl enable --now nginx
> ```
>
> 用 `sudo install -D -m 644 <源> <目标>` 代替 `cp` 也能免掉这一步 —— `install -D` 会自带 `mkdir -p`。

装完 `nginx -t && systemctl reload nginx` 后**访问 IP 却还是发行版的 Nginx 欢迎页**，
是另一个坑：系统自带的默认站点占着 80 端口的 `default_server`，而本站点的
`server_name` 是 `_`（不匹配任何真实 Host），抢不到「默认」位，于是请求被默认站点接走。
移走那份默认站点即可（与 `/v1` 的 SSE 配置无关）：

```bash
sudo rm -f /etc/nginx/sites-enabled/default        # Debian / Ubuntu（软链，删除安全）
# RHEL 系：注释掉 /etc/nginx/nginx.conf 里 `listen 80 default_server;` 那个 server 块
sudo nginx -t && sudo systemctl reload nginx
```

RHEL / CentOS 上「配置全对、请求一律 502」则多半是 SELinux 拦了反代出网：

```bash
sudo setsebool -P httpd_can_network_connect 1
```


前端产物若还没构建（**不构建则浏览器一片空白**）：

```bash
sudo -u llmbridge bash -c 'cd /opt/llmbridge/admin-web && npm ci && npm run build'
# 或用脚本只补这一步（不碰其它任何东西）：sudo bash deploy/install.sh --frontend-only
```

## 七、初始化与验收

首次安装**不需要任何手工初始化步骤** —— `llmbridge-serve` 启动时会自动完成。
下面的表格既可用于验收「自动引导是否生效」，也可用于手工触发时对照。

| 步骤 | 命令 / 接口 | 期望结果 |
|---|---|---|
| 健康检查 | `curl -f localhost:8000/health` | `{"status":"ok"}` |
| 启动引导日志 | 看服务启动日志 | `bootstrap: schema_created=True admin=created eval_cases=created providers=seeded counts={'providers': 24, 'vendors': 13}` |
| 手工触发引导 | `llmbridge-seed` | `seed: 已建表 / 已创建默认管理员 … / 已写入内置评测样本 / 已预置厂商接入目录（通道 24 条 / 厂商 13 家）` |
| 引导幂等复跑 | `llmbridge-seed` | `表已存在，跳过建表` / `管理员已存在，跳过` / `评测样本已存在，跳过` / `厂商接入目录已是最新版本，跳过` |
| 目录预演 | `llmbridge-catalog --dry-run` | 报告「新增 0 / 按名命中 24」，末尾 `（dry-run：已回滚，未写库）` |
| 登录 | `POST /admin/auth/login` `admin/admin123` | 返回 `access_token`；**随后立即改密** |
| 厂商列表 | `GET /admin/providers?page_size=200` | `total=24`，`vendor` 去重后 **13 家**；全部 `enabled=false` / `has_key=false` / `routable=false` |
| 模型池（初始应为空） | `GET /admin/models` | `total=0` —— 需在「模型池」页手工添加后才能路由 |
| 端到端 | 先加模型+填 Key，再 `POST /v1/chat/completions`，`model=auto` | 200；响应头含 `x-router-trace-id` / `x-router-layer` / `x-router-model` |
| 流式 | 同上加 `"stream": true` | 逐块下发，**不是攒完一次性刷出**（后者说明 nginx `proxy_buffering` 没关） |

## 八、环境变量清单

| 变量 | 必填 | 默认（仅开发） | 说明 |
|---|---|---|---|
| `DATABASE_URL` | 是 | `sqlite:///./llmbridge.db` | 生产用 `postgresql+psycopg://...`。**不要写 asyncpg** |
| `POSTGRES_PASSWORD` | compose 必填 | — | 仅 compose 使用，同时初始化 db 与注入 api |
| `HTTP_PORT` | 否 | `8081` | compose 映射到宿主机的控制台端口 |
| `AUTO_BOOTSTRAP` | 否 | `true` | 启动时自动「建表 / 默认管理员 / 内置评测样本 / 厂商接入目录」，均幂等。生产由 DBA 管库时置 `false`，改由运维跑 `llmbridge-seed` |
| `REDIS_URL` | 否 | 空 | 缺省不启用缓存/限流，自动降级 |
| `JWT_SECRET` | **是** | `dev-only-change-me` | 32 字节随机 |
| `ENCRYPTION_MASTER_KEY` | **是** | `dev-only-change-me-32bytes-min!!` | AES-256-GCM 主密钥。**丢失 = 所有已存厂商 Key 永久不可解**，须离线备份，严禁进版本库 |
| `ALLOW_LOCAL_BASE_URL` | 否 | `false` | 是否允许厂商 `base_url` 用 `http://` 及 localhost/私网。**生产必须 false** |
| `JUDGE_PROVIDER` | 否 | `mock` | `mock`（离线可用）/ `jev` |
| `JEV_API_KEY` / `JEV_BASE_URL` | 条件 | 空 / 官方地址 | `JUDGE_PROVIDER=jev` 时必填。注意是 `JEV_` 不是 `JEVA_` |
| `DECIDER_TIMEOUT_MS` | 否 | `3000` | 判定器独立超时 |
| `ROUTE_CONFIDENCE_THRESHOLD_T2` | 否 | `0.5` | L2 置信度低于此值走 L3 |
| `DEFAULT_MODEL_ID` | 否 | `1` | 全部候选失败时的最终默认模型。**必须指向模型池里真实存在的 id** —— 初始模型池是空的，填了不存在的 id 时兜底会失败（不会静默降级） |
| `REQUEST_TIMEOUT_MS` | 否 | `30000` | 上游调用超时 |
| `ENABLE_TOOL_EXECUTION` | 否 | `false` | **默认纯透传**（标准 OpenAI 语义）。开了网关会自己执行 `WebFetch` 并改写正文 |
| `TOOL_RESULT_MAX_CHARS` | 否 | `8000` | 仅上项为 true 时生效 |

> 判定器相关几项也可在控制台「设置」页修改（写入 `sys_config` 表，**库 > .env > 代码默认**，
> 保存即生效，无需重启）。此时 `.env` 与库内值可能不一致，**以控制台显示的来源为准**。

## 九、升级与回滚

```bash
# ---- 升级 ----
tar czf backup-$(date +%F).tgz .env                       # 先备份配置（尤其主密钥）
docker compose --env-file ./.env -f deploy/docker-compose.yml exec db \
    pg_dump -U llmbridge llmbridge | gzip > db-$(date +%F).sql.gz

# 替换代码 → 重新构建 → 重启
docker compose --env-file ./.env -f deploy/docker-compose.yml up -d --build

# 历史库补列（按需，每条都幂等）
python scripts/migrate_add_provider_channels.py
python scripts/migrate_add_sys_config.py

# ---- 回滚 ----
docker compose --env-file ./.env -f deploy/docker-compose.yml down
# 还原上一版镜像 tag 与代码，再：
zcat db-YYYY-MM-DD.sql.gz | docker compose exec -T db psql -U llmbridge -d llmbridge
docker compose --env-file ./.env -f deploy/docker-compose.yml up -d
```

**主密钥绝不能换**：`ENCRYPTION_MASTER_KEY` 一旦变更，库内所有厂商 Key 都解不开，
厂商全部变成「未接入」。换主密钥必须配套重新录入全部 Key。

**容器库形态的升级与回滚**（不涉及代码替换，只换镜像标签）：

```bash
# 升级到新版本
sed -i 's/^LLMBRIDGE_TAG=.*/LLMBRIDGE_TAG=1.0.1/' .env
docker compose --env-file ./.env -f deploy/docker-compose.image.yml pull
docker compose --env-file ./.env -f deploy/docker-compose.image.yml up -d

# 回滚：把 LLMBRIDGE_TAG 改回上一版的**不可变标签**（形如 1.0.0-<git短sha>），重跑上面两行
```

数据卷不动，所以回滚不需要动数据库；新增列由启动引导幂等补齐。若要连数据一起回退，
仍按上面的 `pg_dump` 流程还原。**回滚时务必用不可变标签**——浮动标签可能已被新版本覆盖。

## 十、常见问题

| 现象 | 原因与排查 |
|---|---|
| **流式「一直转圈，最后一次性刷出」** | nginx `proxy_buffering` 没关。用 `curl -N` 直打 8000 对比：直连正常 = 反向代理问题 |
| **服务能起、`/health` 200，但一登录就 500** | Windows 上没带 `--loop app.core.eventloop:selector_loop_factory`，跑的是 ProactorEventLoop。启动日志里有一行 `event_loop=... psycopg_compatible=False` 会直接点出来 |
| 启动报 `ModuleNotFoundError: No module named 'app.xxx'` | 该子包缺 `__init__.py`。setuptools 的 `packages.find` 依赖它，会静默漏包 |
| `database is locked` | 用了 SQLite 且多 worker。生产换 PostgreSQL |
| 日志里 token / 成本是 0 | 流式请求且上游未回 `usage`（客户端没传 `stream_options.include_usage`）。是**缺数据**，不是零消耗 |
| 控制台「厂商接入」空白 | 启动引导没跑成功。先看启动日志有没有 `bootstrap: ... providers=seeded`；没有就手工跑 `llmbridge-seed` 看报错。**注意 `AUTO_BOOTSTRAP=false` 时会跳过自动引导**，需显式跑一次 |
| 控制台「模型池」空白 | **这是初始预期状态，不是缺陷** —— 首次安装只预置接入商，模型需在「模型池」页手工添加（或 `llmbridge-catalog --with-models` 灌参考目录）。没有模型时路由候选池为空，`/v1` 会走兜底并如实报错 |
| 「厂商接入」里 `routable=false` 全是灰的 | 同样是预期：预置的是「目录」不是「已接入」，`enabled=false` + 占位密钥。**填一个 API Key 即自动启用**该通道 |
| 容器报 `/bin/sh^M: not found` | `entrypoint.sh` 被存成了 CRLF。见 `.gitattributes`，仓库里已强制 LF |
| 打包时 npm 报「找不到」 | Node 未装或不在 PATH；或已构建过 `dist/` 时改用 `--skip-frontend` |
| **方式一装完提示「控制台地址 尚未就绪（缺前端构建）」** | 说明脚本没能备好 Node.js（网络不通 / 无包管理器）。按提示重跑 `sudo bash /opt/llmbridge/deploy/install.sh --frontend-only` 即可 —— 它会自动装 Node.js、构建前端，并把 Nginx 一并补齐。要指定镜像源：追加 `--npm-registry https://registry.npmmirror.com`；要指定 Node 版本：`--node-version v22.14.0` |
| 前端打开是白屏、assets 404 | `admin-web/dist` 没构建或没挂载。nginx 的 `root` 指向它 |
| **手工部署 Nginx 时才需要看下面三条**（方式一里这三件都由 `install.sh` 自动处理） | ↓ |
| **`cp <站点配置> /etc/nginx/conf.d/llmbridge.conf` 报「没有那个文件或目录」** | **这台机器没装 Nginx** —— 该报错说的是**目标目录**缺失（源文件缺失时报的是「无法获取 … 的状态」）。方式一会自动安装；手工部署时先 `dnf install -y nginx`（RHEL 系）或 `apt-get install -y nginx`（Debian 系），也可把 `cp` 换成 `install -D -m 644`（自带 `mkdir -p`） |
| **站点配好、`nginx -t` 与 `reload` 都成功，访问 IP 却是 Nginx 欢迎页** | 系统自带的默认站点占着 80 的 `default_server`，本站点 `server_name` 是 `_`（不匹配任何真实 Host），抢不到默认位。方式一会自动移走它；手工部署时：Debian/Ubuntu 删 `/etc/nginx/sites-enabled/default`，RHEL 系摘掉 `nginx.conf` 里默认 server 的 `default_server` 标记。与 `/v1` 的 SSE 配置无关 |
| RHEL / CentOS 上配置看着没错、请求却一律 502 | SELinux 拦了反代出网：`setsebool -P httpd_can_network_connect 1`（方式一自动执行） |
| **控制台打开即 `403 Forbidden`（nginx 配置本身正确）** | 两类原因任一缺失都会 403：① **SELinux 上下文**（Enforcing 下只标了 `…/admin-web/dist`、漏父目录 `admin-web` 与安装根 `/opt/llmbridge`，traverse 被拦）→ 应急 `sudo semanage fcontext -a -t httpd_sys_content_t "/opt/llmbridge/admin-web(/.*)?"; sudo semanage fcontext -a -t httpd_sys_content_t "/opt/llmbridge"; sudo restorecon -R /opt/llmbridge/admin-web; sudo restorecon /opt/llmbridge`（方式一从 V1.6.9 起自动整条路径打标 + 持久化）；② **DAC 权限**：构建产物被 `umask 077` 弄成 `600`/`700`（目录 `drwx------`），nginx 用户进不去也读不到 → 应急 `sudo chmod -R u+rwX,go+rX /opt/llmbridge/admin-web && sudo chmod o+x /opt/llmbridge /opt/llmbridge/admin-web`（方式一从 V1.6.10 起在 `ensure_nginx` 探活前无条件纠正，且覆盖「重跑跳过构建」的情形） |

## 十二、发布到 GitHub

仓库**已在本地初始化完毕**（分支 `main`，含首次提交），只差一个远端。

### 12.1 先在网页端建空仓库

打开 <https://github.com/new> 创建仓库，**不要勾选** “Add a README file”、
“.gitignore template”、“license”——本地这三样都已存在，勾了会产生冲突，
首次 push 只能强推（`--force`）才能解决。

### 12.2 关联远端并推送

```bash
cd <仓库目录>
git remote add origin https://github.com/<你的账号>/llmbridge.git
git branch -M main
git push -u origin main
```

认证用 **Personal Access Token**（Settings → Developer settings → Personal access
tokens，勾 `repo` 权限）或 **SSH key**；GitHub 自 2021-08 起不再接受账号密码推送。

已装 GitHub CLI 的话可以一条命令完成建仓 + 关联 + 推送：

```bash
gh repo create llmbridge --private --source=. --remote=origin --push
```

### 12.3 推送前必查（密钥泄露是唯一不可逆的事故）

```bash
# 1) 确认 .env 没有被跟踪（正常应无输出）
git ls-files | grep -E '\.env$'

# 2) 确认没有本地数据库与日志
git ls-files | grep -E '\.(db|log)$|\.db-'

# 3) 确认忽略规则生效
git check-ignore -v .env .venv/ node_modules/ release/ build/ .workbuddy/
#    每一项都应打印命中的 .gitignore 行号

# 4) 全量扫描疑似密钥（正常应无输出）
git grep -nEI 'ENCRYPTION_MASTER_KEY *= *[^d]|sk-[A-Za-z0-9]{20,}' -- . \
  ':!docs' ':!*.md'
```

**若已经误推了 `.env`**：仅删除文件再提交是不够的（历史里仍可检出）。
必须视为密钥泄露处理 —— **立即轮换 `ENCRYPTION_MASTER_KEY` 之外的所有凭证**，
并把 `ENCRYPTION_MASTER_KEY` 场景按「更换主密钥 = 全部厂商 Key 需重新录入」处理
（见 §九）。历史清理需 `git filter-repo` 或 BFG，且要通知所有协作者重新克隆。

### 12.4 仓库里刻意不入库的东西

| 条目 | 原因 |
|---|---|
| `.env` | 含 `ENCRYPTION_MASTER_KEY` 与数据库密码 |
| `.venv/`、`node_modules/` | 体积（数万文件），且可由锁文件重建 |
| `*.db*`、`*.log`、`request_log_dropped.json` | 本地运行状态 |
| `release/`、`build/`、`*.egg-info/` | 构建产物，按需重新生成 |
| `.workbuddy/` | 本地工作区元数据 |
| `admin-web/dist/` | 构建产物；生产由 nginx 挂载，随发布包交付 |
| `admin-web/tsconfig.tsbuildinfo` | TS 增量编译缓存，每次构建都变 |
