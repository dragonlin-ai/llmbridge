## 二、日常运维

```bash
docker compose -f deploy/docker-compose.yml ps          # 容器状态
docker compose logs -f api --tail 200                   # 应用日志
curl -f http://localhost:8000/health                    # 存活
docker compose exec db pg_isready -U llmbridge          # PG
docker compose exec redis redis-cli ping                # Redis
tail -f /var/log/nginx/error.log                        # Nginx 错误
df -h && docker system df                               # 磁盘（日志增长监控）
```

结构化日志按行 JSON：`grep '"event":"fallback"' api.log | tail` 快查近期降级。

## 三、备份管理

| 对象 | 命令/策略 | 频率 |
|---|---|---|
| PostgreSQL | `docker compose exec db pg_dump -U llmbridge llmbridge \| gzip > backup_$(date +%F).sql.gz` | 每日 |
| 恢复 | `gunzip -c backup_xxx.sql.gz \| docker compose exec -T db psql -U llmbridge llmbridge` | 演练每季 |
| Redis | RDB 默认即可（**只存可重建数据，丢失无业务影响**） | - |
| .env + ENCRYPTION_MASTER_KEY | **离线介质双份**。主密钥丢失 = 全部厂商 API Key 永久不可解 | 变更即备 |

## 四、故障处理

| 故障 | 排查路径 |
|---|---|
| api 无法启动 | `docker compose logs api`；高频原因：alembic 失败（DB 未就绪）、.env 缺必填、master_key 与密文不匹配 |
| PG 连接池耗尽 | `SELECT count(*) FROM pg_stat_activity;`；确认 gunicorn worker 数 × 池大小 < max_connections；慢查询看 `pg_stat_statements` |
| Redis 不可用 | **非紧急**（降级设计，功能全可用，仅无缓存/限流）。恢复后自动回归 |
| 上游大面积 429/超时 | 日志 `fallback_reason` 分布 → 定位厂商 → 控制台临时停用该厂商模型（流量自动切备选） |
| 路由准确率骤降 | ① 查 `request_log.router_output_json` 的 task_type 分布是否漂移 ② Jev→Mock 是否误切 ③ 最近是否改了规则/能力标签 ④ 用 eval_case 跑批对比历史 |
| 兜底率异常升高 | 90% 是 DECIDER_UNAVAILABLE 或 LOW_CONFIDENCE 集中爆发：查判定器连通性与 T2 配置是否被改 |
| 密钥解密失败 | **高危**。核对 ENCRYPTION_MASTER_KEY 是否被更换；禁止「换密钥重启」操作，先走密钥轮换流程（V1.1 提供） |

## 六、关键指标与告警阈值

| 指标 | 口径 | 建议告警阈值 |
|---|---|---|
| 路由额外延迟 P95 | request_log.route_latency_ms | >800ms 持续 10min |
| 兜底率 | fallback_reason 非空占比 | >10%（基线目标接近 0 的异常兜底） |
| 降级率 | UPSTREAM_UNAVAILABLE 占比 | >5% |
| 单模型错误率 | 上游 4xx/5xx 分模型 | >20% 持续 5min（联动停用建议） |
| /health | HTTP 200 | 失败 3 次 |
| 成本日增 | sum(cost) 按天 | 较 7 日均值 +100% |
| 磁盘 | 日志与 PG 卷 | >80% |

告警通道 MVP 用日志关键字 + 外部巡检脚本；接入钉钉/企微 webhook 列 V1.1。
