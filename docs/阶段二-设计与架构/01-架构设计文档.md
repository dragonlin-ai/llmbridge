## 一、架构风格与原则

**前后端分离 + 分层架构 + 策略模式。**

三条不变式（与基线 3.11 边界约定一一对应）：

1. **双入口分离**：`/v1`（对外，禁止透出 5xx，错误信息最小化）与 `/admin`（对内，JWT 鉴权，错误信息完整）永不合流。
2. **内核唯一**：试跑台与线上请求执行**同一段** `router_engine` 代码，试跑台的验证结论对线上有效。
3. **差异收敛**：厂商协议/流式差异只存在于 `adapters/`；判定模型差异只存在于 `deciders/`。

## 三、模块划分与职责

| 模块（app/ 下） | 职责 | 核心接口/类 |
|---|---|---|
| `api/v1/` | 对外 OpenAI 兼容入口；鉴权、限流、SSE 透传；组装 `x-router-*` 响应头 | `router = APIRouter(prefix="/v1")` |
| `api/admin/` | 控制台 9 组接口；JWT 鉴权；分页/筛选 | 按资源拆 `providers.py / models.py / rules.py / samples.py / logs.py / stats.py / route_preview.py / auth.py` |
| `router_engine/` | 三层路由编排；每层返回 `Decision` 或 `None`，短路即返回 | `pipeline.py`、`l1_rule.py`、`l2_jev.py`、`l3_fallback.py` |
| `deciders/` | 判定器抽象与实现；**至少两个实现**（官方 Jev + Mock）通过同一契约测试 | `base.py: BaseDecider`、`jev_decider.py`、`mock_decider.py` |
| `adapters/` | 厂商协议隔离；流式/非流式统一；降级重试 | `base.py: BaseAdapter`、`openai_compat.py` |
| `services/` | 计费核算、配额与路由缓存（Redis，可降级）、连通性测试 | `billing.py`、`quota_cache.py` |
| `db/` | SQLAlchemy ORM（8 张表）与异步会话 | `tables/*.py`、`session.py` |
| `schemas/` | Pydantic 出入参 | 按接口域分文件 |
| `core/` | 配置（Pydantic Settings）、密钥加解密（AES-256-GCM）、日志 | `config.py`、`security.py` |
| `observability/` | trace_id 生成与上下文传递、结构化日志 | `trace.py` |

## 四、关键数据结构（跨层契约）

```python
# app/router_engine/context.py
@dataclass
class RouterContext:
    trace_id: str
    input_text: str
    token_len: int
    session_id: str | None
    candidates: list[ModelOut]      # enabled 模型按 priority 升序
    hit_layer: str | None           # L1 / L2 / L3
    decision: Decision | None       # 判定器输出
    final_model: ModelOut | None
    fallback_reason: str | None
    route_started_at: float

# app/deciders/base.py
@dataclass
class Decision:
    task_type: str
    confidence: float
    probabilities: dict[str, float]
    features: dict[str, float]      # complexity / has_code / is_sensitive
    decider: str                    # jev / mock —— 落库到 router_output_json

class BaseDecider(ABC):
    @abstractmethod
    async def decide(self, ctx: RouterContext) -> Decision | None: ...
    @abstractmethod
    async def health_check(self) -> bool: ...
```

**判定映射（task_type → model 选择）**：L3 内置权重函数 `score = w_acc·capability_match + w_cost·cost_rank + w_lat·latency_rank`，MVP 固定权重 (0.6, 0.25, 0.15)；候选集为 `capabilities` 含 `task_type` 的 enabled 模型，空集时回退全部 enabled 模型，再空则 `DEFAULT_MODEL_ID`。

## 五、请求时序（含流式）

```
第三方        api/v1         pipeline        deciders       adapters        上游
  │  POST       │               │               │              │             │
  ├────────────▶│ 鉴权/限流/校验 │               │              │             │
  │             ├─ ctx ────────▶│ L1 规则(0ms)  │              │             │
  │             │               ├─ 未命中 ─────▶│ Jev 判定      │             │
  │             │               │   70~500ms    ├─ Decision    │             │
  │             │               ◀── L3 映射选型 ─┤              │             │
  │             │◀─ final_model ┤               │              │             │
  │             ├──────────────────────────────────────────────▶│ chat/stream │
  │◀══════════════════════════ SSE/JSON 回流（x-router-* 头已随首包发出）═════│
```

**流式硬约束**：`chat_stream()` 是异步生成器，首包产生前 pipeline 必须已完成（基线：不允许先返回再改道）；生成器 `finally` 中必须释放上游连接并落 request_log。

## 六、技术选型与理由

| 层 | 选型 | 理由 |
|---|---|---|
| 决策模型 | Jev 官方 API（`BaseDecider` 后面） | 需求指定；校准置信度可用；Mock 实现保开发/内网可跑 |
| Web 框架 | FastAPI + Pydantic v2 | 异步原生（SSE 必需）；自动 OpenAPI 文档；校验一体 |
| ORM | SQLAlchemy 2.x + Alembic | 2.0 风格 typed ORM；迁移可回滚 |
| 数据库 | SQLite（开发）→ PostgreSQL（生产） | 基线 3.7 固定。生产理由：写并发（多 worker 共享写锁不可行）、JSONB 查询 `router_output_json`、分区能力 |
| 缓存 | Redis | 路由幂等缓存 `route:cache:{sha256(input_text)}`（TTL 1h）、限流/配额计数。**只存可重建数据**，Redis 故障自动降级为不缓存（TR-012） |
| HTTP 客户端 | httpx.AsyncClient（单例连接池） | 异步 + 流式 + 超时精细控制 |
| 安全 | AES-256-GCM（密钥加密）+ bcrypt（口令）+ JWT | 见《06-安全方案文档》 |
| 前端 | Vue3 + Vite5 + TS + Pinia + Element Plus + ECharts | 见《03-前端技术设计说明书》 |

## 七、部署架构

```
开发(Windows)：uvicorn app.main:app --port 8000 --loop app.core.eventloop:selector_loop_factory
               ⚠️ --loop 不可省略：Windows 下 psycopg3 拒绝 ProactorEventLoop（uvicorn 不带
                  --reload 时会选它），省略则服务能启动但一访问数据库即 500。详见技术实现文档 K-05
                 +  npm run dev :5173（Vite 代理）
生产(Linux)：Nginx(80/443) ──静态──▶ admin-web/dist
              └─/v1,/admin──▶ gunicorn -k uvicorn.workers.UvicornWorker -w 4 :8000
                                   ├──▶ PostgreSQL（异步驱动 psycopg3）
                                   └──▶ Redis
```

> 数据库：开发与生产**统一 PostgreSQL**（2026-09-22 起）。SQLite 仅在无 `.env` 时作零依赖兜底，
> 不再作为开发主库——避免「开发用 SQLite、生产用 PG」两套语义导致的行为差异
> （典型：SQLite 无原生 BOOLEAN/DATETIME、外键约束需 PRAGMA 才生效）。

Nginx 对 `/v1/` 必须 `proxy_buffering off`（SSE 卡顿首因）；详见《01-部署文档》（阶段五）。

## 八、技术风险与对策

| 风险 | 对策 |
|---|---|
| Jev 官方 API 未对中国大陆开放，网络不可达 | `deciders` 双实现 + 启动时 health_check 探测，失败自动切 Mock 并打 WARN 日志；**部署形态决策仍待 HD 确认（遗留卡点）** |
| L2 判定延迟抖动导致 P95 超 800ms | 路由缓存前置查询；decider 独立超时 3s；超时按低置信走 L3 |
| request_log 单表膨胀 | 异步批量写（50 条/1s 刷盘）；生产按月分区；input_text 落库截断 2000 字符 |
| SQLite 多 worker 写锁 | 开发期单 worker + WAL；性能压测一律在 PostgreSQL 上执行（SQLite 数字不具可比性） |
