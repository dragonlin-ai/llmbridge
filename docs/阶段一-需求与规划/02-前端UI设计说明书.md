## 一、设计原则

### 1.1 设计理念

这是一个**给工程师用的控制台**，不是给普通用户用的产品页。因此设计理念是：

> **让「配置一个路由策略」和「搞清一次请求为什么走了这个模型」这两件事变得尽可能快。**

具体体现为三条原则：
1. **操作路径短**：高频操作（新增规则、试跑、查日志）不超过 2 次点击可达。
2. **信息密度优先**：一屏尽量多给有效信息，不做过多留白与装饰。
3. **决策可解释**：凡是有系统判断的地方（路由层级、模型选择、降级），都必须把「为什么」显式呈现出来。

### 1.2 设计风格

- **视觉风格**：简约专业的技术控制台，深色代码块 + 浅色主体，强调数据表格与状态标识。
- **交互风格**：高效快捷，面向熟练用户，默认支持键盘操作（Enter 提交、Esc 关闭弹窗）。
- **状态可视化**：用颜色与图标明确区分「命中 / 跳过 / 兜底 / 降级」这类系统行为状态。

### 1.3 色彩方案

**主色调**：`#409EFF`（Element Plus 默认蓝）

**使用场景**：
- 主按钮、链接、选中态、关键数据强调
- 侧边栏选中菜单项

**辅助色**：

| 颜色 | 色值 | 用途 |
|------|------|------|
| 成功绿 | `#67C23A` | L1 规则命中、模型可用、请求成功 |
| 警告黄 | `#E6A23C` | 低置信兜底、缓存未命中、模型响应偏慢 |
| 危险红 | `#F56C6C` | 模型降级发生、模型不可用、请求失败、密钥异常 |
| 信息灰 | `#909399` | 跳过层级、禁用状态、次要说明文字 |
| 深度紫 | `#7F77DD` | L2 Jev 判定链路标识（与主色区分） |

**路由层级配色约定（全局统一）**：

| 层级 | 色值 | 含义 |
|------|------|------|
| L1 | `#67C23A` | 规则短路，最快最省 |
| L2 | `#7F77DD` | Jev 决策判定 |
| L3 | `#F56C6C` | 组合选型与兜底（异常路径） |

**深色模式**：作为可选主题（跟随系统 `prefers-color-scheme`），MVP 阶段提供基础适配，路由层级配色保持不变。

│ ▸ 路由规则配置 │  │                                          │  │
│ ▸ 路由试跑台   │  │  数据表格 / 表单 / 图表 / 可视化组件       │  │
│ ─────────    │  │                                          │  │
│ ▸ 决策样本管理 │  │                                          │  │

- 侧边栏宽度 208px，可折叠为 64px（图标模式）。
- 主内容区最小宽度 1024px，超出部分横向滚动。
- 底部状态栏常驻，实时展示服务健康与模型池可用数——这是运维视角的最小信息面。

### 2.2 页面结构

#### 登录页

- 布局说明：居中卡片，无顶部栏与侧边栏。
- 页面元素：系统名称与 Logo、用户名输入框、密码输入框、「登录」按钮、错误提示条。

#### 概览 Dashboard（P1）

- 布局说明：顶部 4 个指标卡一行，下方左右分栏（左：路由层级分布饼图 + 请求量趋势折线；右：Top 模型用量榜 + 最近异常请求列表）。
- 页面元素：4 个 KPI 卡（今日请求量 / 今日成本 / 路由准确率 / 平均路由延迟）、路由层级分布图、请求量趋势图、模型用量榜、异常请求列表（含兜底与降级）。

#### 模型池管理（P0）

- 布局说明：上方厂商接入点卡片列表，下方该厂商下的模型表格。
- 页面元素：接入点卡片（名称 / base_url / 状态灯 / 连通性测试按钮）、模型表格列（模型名 / 显示名 / 能力标签 / 输入单价 / 输出单价 / 上下文窗口 / 优先级 / 启用开关 / 操作）、「新增接入点」「新增模型」按钮。

#### 路由规则配置（P0）

- 布局说明：左侧规则列表（可拖拽排序），右侧规则详情与条件编辑器。
- 页面元素：规则列表项（优先级序号 / 规则名 / 类型标签 / 目标模型 / 启用开关 / 拖拽手柄）、条件编辑器（可视化条件行 + 实时生成的 JSON 预览）、规则命中测试（内嵌输入框可直接试跑该条规则）。

#### 路由试跑台（P0，核心页面）

- 布局说明：上方输入区，下方结果区分四块——链路条、Jev 判定概率分布、候选打分行、原始 JSON。
- 页面元素：
  - 输入区：多行文本框、`session_id` 输入（可选）、《试跑》按钮、示例文本快捷填充
  - 链路条：`L1 → L2 → L3` 三段可视化条，命中段高亮并终止，跳过段灰显并标注跳过原因
  - 结果摘要：`hit_layer` / `task_type` / `selected_model` / `confidence` / `latency_ms` / `trace_id`
  - Jev 判定概率分布：`task_type` 各候选类别的概率条形图 + 特征标记（`complexity` / `has_code` / `is_sensitive`），提供复制按钮。**这是替代原「判定理由」的可解释性区域**
  - 候选打分行：候选模型列表，每项显示 `model_id`、综合得分（进度条）、命中的映射规则与**落选原因**
  - 原始响应：可折叠的 JSON 原文

#### 决策样本管理（P1）

- 布局说明：上方标签分布统计，下方样本表格。
- 页面元素：标签分布柱状图、样本表格（文本摘要 / 实际 `task_type` / 实际选用模型 / 来源 / 操作）、批量导入按钮。
- **说明**：样本由线上 `request_log` 的判定结果沉淀而来（`decision_sample` 表），用途是扩充 `eval_case` 评测集与优化 Jev 的 `criteria` 描述，**不再承担 embedding 向量化职责**（L2 语义召回已移出 MVP）。

#### 调用日志（P0）

- 布局说明：上方筛选栏，中间日志表格，点击行右侧滑出 Trace 抽屉。
- 页面元素：筛选栏（时间范围 / 模型 / 命中层级 / 状态 / 关键词 / trace_id）、日志表格列（时间 / trace_id / 输入摘要 / 命中层级 / 最终模型 / 路由延迟 / 总延迟 / 状态 / 是否兜底）、Trace 抽屉（时间轴 + 判定详情 + 降级原因）。

#### 评测看板（P1）

- 布局说明：上方可选评测集与《开始评测》按钮，下方准确率指标与混淆矩阵。
- 页面元素：评测集选择、准确率大数字、混淆矩阵热力图、错判样本列表（输入 / 期望模型 / 实际模型 / 差异原因）。

#### 用量与成本（P2）

- 布局说明：上方时间维度切换与成本总额，下方按模型/时间的成本堆叠图与明细表。
- 页面元素：时间维度切换（日 / 周 / 月）、成本堆叠柱状图、模型用量明细表（模型 / 调用次数 / prompt tokens / completion tokens / 成本 / 占比）。

## 三、组件设计

### 3.1 基础组件

采用 Element Plus 组件库，统一使用其中以下基础组件：

**按钮**
- 主要按钮（Primary）：用于页面主操作，如《保存》《试跑》《登录》
- 次要按钮（Default）：用于取消、返回
- 危险按钮（Danger）：用于删除接入点、删除规则
- 链接按钮（Link）：用于表格行内的「查看」「编辑」操作

**表单组件**
- 输入框（Input / InputNumber）：文本、数值、密钥（password 类型 + 掩码）
- 下拉选择（Select）：模型选择、层级筛选、类型选择
- 开关（Switch）：模型启停、规则启停
- 多选标签（Select multiple / Tag input）：能力标签
- 日期时间选择器（DatePicker）：日志筛选的时间范围

**反馈组件**
- 提示（ElMessage）：操作成功 / 失败的轻提示
- 弹窗（ElDialog）：新增 / 编辑表单、删除二次确认
- 抽屉（ElDrawer）：Trace 详情、规则详情
- 加载（ElLoading / 骨架屏）：页面与表格加载
- 空状态（ElEmpty）：无数据、无样本、无日志
- 结果页（ElResult）：试跑异常、连通性测试失败

### 3.2 业务组件

#### 3.2.1 路由链路可视化条 `RouteChainBar`

- **功能说明**：以三段横条展示 L1→L2→L3 的执行过程，明确指出在哪一层命中终止、其余各层为何被跳过。这是控制台最具辨识度的组件。
- **Props**：

| 名称 | 类型 | 必填 | 说明 |
|------|------|------|------|
| hitLayer | `'L1' \| 'L2' \| 'L3'` | 是 | 命中的层级 |
| details | `Array<{layer, status, explain, latencyMs}>` | 是 | 每层状态：`hit` / `skipped` / `failed` |
| showLatency | `boolean` | 否 | 是否在每段下方显示该层耗时，默认 true |

- **交互设计**：
  - 命中段以对应层级主色填充，段内显示「命中」与目标模型名。
  - 跳过段灰显，段内显示「跳过」，鼠标悬停显示跳过原因气泡。
  - 失败段（如 L2 判定器超时）红显，悬停显示错误信息。
  - 点击任意段可展开该层详情（输入、输出、耗时）。

#### 3.2.2 候选模型打分行 `CandidateScoreRow`

- **功能说明**：展示路由判定给出的各候选模型及匹配分数，让用户判断「是不是分数太接近导致误判」。
- **Props**：

| 名称 | 类型 | 必填 | 说明 |
|------|------|------|------|
| candidates | `Array<{modelId, displayName, score, matchedRule, enabled}>` | 是 | 候选列表 |
| selectedModelId | `string` | 否 | 最终选中的模型，用于高亮 |

- **交互设计**：
  - 按 `score` 降序排列，最终选中的模型置顶并加高亮边框。
  - 分数以进度条呈现（0~1 映射为 0~100%），最高分候选以成功绿呈现。
  - 被合规条件或能力标签过滤掉的候选灰显，并标注落选原因（如「合规拦截」「无代码能力」）。
  - 悬停显示 `matchedRule`。
  - 分数差距 < 0.1 时，在行尾显示警告图标提示「分数接近，选型对权重配置敏感」。

#### 3.2.3 条件规则编辑器 `RuleConditionEditor`

- **功能说明**：让非开发人员也能配置 `route_rule.condition_json`，同时保证生成的条件一定是合法 JSON。
- **Props**：

| 名称 | 类型 | 必填 | 说明 |
|------|------|------|------|
| modelValue | `RuleCondition` | 是 | 条件对象（v-model） |
| ruleType | `'keyword' \| 'regex' \| 'token_len' \| 'tenant' \| 'session'` | 是 | 规则类型，决定可选字段与运算符 |

- **交互设计**：
  - 可视化条件行：`[字段 ▾] [运算符 ▾] [值输入框]`，支持「+ 添加条件」与多条件 AND / OR 切换。
  - 右侧实时渲染生成的 JSON 预览（只读代码块），并做合法性校验，不合法时禁止保存。
  - 提供《用当前条件测试》按钮，内嵌输入框可直接看到该条件是否命中目标文本。

#### 3.2.4 Trace 时间轴 `TraceTimeline`

- **功能说明**：以时间轴方式还原一次请求的完整决策过程，是排查「为什么走了这个模型」的最终依据。
- **Props**：

| 名称 | 类型 | 必填 | 说明 |
|------|------|------|------|
| trace | `TraceDetail` | 是 | 含各阶段耗时、路由判定详情、降级原因、token 与成本 |

- **交互设计**：
  - 时间轴节点：请求进入 → 鉴权 → L1 → L2 → L3 → 上游调用 → 响应下发。
  - 每个节点显示耗时（毫秒），耗时占比过大的节点以警告色高亮。
  - L2 节点展开后显示 Jev 的 `probabilities` 概率分布与 `confidence`；L3 节点显示候选排序与选型依据 `explain`。二者均可复制。
  - 发生降级时，额外插入一个红色节点显示 `fallback_reason` 与原始目标模型。

#### 3.2.5 接入点状态卡 `ProviderCard`

- **功能说明**：展示厂商接入点的健康状态与快捷操作。
- **Props**：

| 名称 | 类型 | 必填 | 说明 |
|------|------|------|------|
| provider | `{id, name, baseUrl, enabled, keyMasked, health}` | 是 | 接入点信息，`health` 为 `unknown` / `healthy` / `unhealthy` |

- **交互设计**：
  - 状态灯三态：灰（未测试）、绿（健康）、红（不可用）。
  - 《连通性测试》按钮点击后按钮进入 loading，返回后在卡片内展示耗时与错误原因。
  - API Key 仅以掩码展示（`sk-****abcd`），无任何「显示明文」入口。

## 四、交互设计

### 4.1 交互流程

**流程一：配置模型池**

```
进入模型池管理 → 新增接入点（填名称/base_url/API Key）
  → 点击连通性测试 → 状态灯变绿
  → 新增模型（选接入点/填模型名/能力标签/单价/优先级）
  → 启用模型 → 模型进入路由候选集
```

**流程二：配置路由规则**

```
进入路由规则配置 → 点击新增规则
  → 选择规则类型 → 用条件编辑器配置条件
  → 选择目标模型 → 用当前条件测试命中效果
  → 保存 → 规则列表出现，拖动调整优先级
```

**流程三：试跑验证（核心流程）**

```
进入路由试跑台 → 粘贴一段真实文本
  → 点击试跑（按钮进入 loading，通常 < 1s）
  → 链路条展示命中层级（如 L2 高亮，L1 灰显并标注跳过原因）
  → 查看 Jev 概率分布确认判定是否合理（如 `code_generation: 0.87` 是否与实际语义相符）
  → 查看候选打分行确认打分与落选原因是否合理
  → 若判定不符预期 → 回到规则配置调整 / 优化 Jev 的 `criteria` 描述
  → 再次试跑，直到符合预期
```

**流程四：排查一次异常请求**

```
进入调用日志 → 用「是否兜底 = 是」筛选
  → 点击目标行 → 右侧滑出 Trace 抽屉
  → 时间轴定位到 L3 节点 → 查看 fallback_reason
  → 若是 UPSTREAM_UNAVAILABLE → 去模型池确认该模型状态
  → 若是 LOW_CONFIDENCE → 去决策样本管理查看同类样本的判定分布，考虑优化 `criteria` 描述
  → 若是 DECIDER_UNAVAILABLE → 检查 Jev 判定器连通性与健康状态
```

### 4.2 动画效果

| 动画类型 | 用途 | 时长 |
|---------|------|------|
| 淡入淡出 | 页面切换、抽屉展开 | 300ms |
| 滑入滑出 | 侧边栏折叠、Trace 抽屉 | 200ms |
| 进度条增长 | 候选模型打分行渲染 | 400ms |
| 链路条逐段点亮 | 试跑结果展示（L1→L3 依次点亮，模拟执行过程） | 每段 120ms，共约 400ms |
| 缩放 | 按钮点击反馈 | 150ms |

### 4.3 反馈机制

- **操作成功**：右上角轻提示（如「规则已保存，下一请求即生效」）。**保存类操作必须提示生效时机**，避免用户误以为要重启。
- **操作失败**：轻提示 + 表单字段下方红色错误文字，同时保留用户已填内容不做清空。
- **加载状态**：表格用骨架屏；按钮用 loading 图标并禁用，防止重复提交；试跑超过 1s 时显示「Jev 判定响应较慢，请稍候」的提示文案。
- **确认操作**：删除接入点、删除规则、禁用正在被引用的模型，均需二次确认，且确认弹窗中明确列出影响范围（如「该模型当前被 2 条规则引用」）。
- **危险信息强调**：发生兜底与降级的请求，在列表中必须带红色角标，不允许静默。
