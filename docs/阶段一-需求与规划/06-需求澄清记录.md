**项目名称**：LLM 路由中转系统（代号 llmbridge）
**版本号**：V1.0
**创建日期**：2026-09-21
**创建人**：HD（齐活林，交付总监）｜ SDA（系统设计数字员工）

## 一、澄清背景

### 1.1 需求原始表述（HD 口述）

> 「现在出来了一个叫 Jev 的大模型，我想通过一个中转系统输入一段文字，先通过 Jev 这个大模型进行判断调用哪个大模型，然后再调用这个大模型返回给用户。」

### 1.2 本次澄清要解决的问题

在阶段一初稿中，路由判定采用的是「**由普通 LLM 充当裁判**」的方案：需要强制 JSON Schema 输出、`temperature=0` 保持稳定、Pydantic 二次校验、解析失败兜底。这一整套设计的存在前提是「**LLM 会吐非法 JSON**」。

HD 明确判定模型为 **Jev** 后，该前提不再成立，原设计中的大量防御性工程随之失效。本文记录这一变更的事实依据、决策结论与影响分析。

## 二、Jev 模型档案（事实核查）

> 本节内容经 WebSearch 与 TypeSafe AI 官方文档核实，来源包括 `docs.typesafe.ai`、TypeSafe AI 官方博客、央广网报道等。**标注为「厂商自报」的数据未经独立验证。**

### 2.1 基本信息

| 项 | 内容 |
|---|---|
| 名称 | Jev |
| 出品方 | TypeSafe AI（旧金山） |
| 创始人 | Diogo Almeida（前 OpenAI 研究员，参与 ChatGPT / RLHF / InstructGPT 相关研究） |
| 发布时间 | 2026-09-15（早期访问） |
| 产品定位 | **System One 模型** —— 面向「快速判断」而非「长文推理」的模型类别，命名取自卡尼曼快慢思考理论 |
| 命名由来 | 经济学家杰文斯（Jevons）与「杰文斯悖论」 |
| 核心特征 | **不生成任何文本**，只输出带校准概率的类型化判定结果 |

### 2.2 三种提问原语

| 原语 | 目的 | 返回字段 |
|---|---|---|
| **Choice** | 从固定选项列表中选一个 | `choice` / `probabilities` / `confidence` |
| **Score** | 按 rubric 对内容打分 | `score` / `probabilities` / `confidence` |
| **Noul** | 判断一个陈述是否成立 | `noul`（0~1） |

三种原语**可以在一次 API 调用中混合提问，并行评估**。官方明确说明：增加提问数量几乎不增加响应时间，且不会产生 context rot。

### 2.3 接入方式

```
POST https://api.typesafe.ai/v1/systemone
Authorization: Bearer <TYPESAFE_API_KEY>
Content-Type: application/json

{
  "state": "<待判定的非结构化文本>",
  "model": "jev-latest",
  "questions": { "<问题 id>": { "type": "choice|score|noul", ... } }
}
```

响应结构：

```json
{
  "model": "jev-1.13.0",
  "answers": {
    "<问题 id>": { "type": "choice", "choice": "...", "confidence": 0.87, "probabilities": { "...": 0.87 } }
  },
  "usage": { "input_tokens": 392, "output_tokens": 65 }
}
```

其他接入渠道：官方 Python SDK `typesafe-sdk`（需 Python ≥ 3.10）、LangChain（`TypeSafeClassifier`）、Vercel AI Gateway、OpenRouter 渠道。

### 2.4 性能与成本（厂商自报）

| 指标 | 数值 |
|---|---|
| 端到端延迟 | 70 ~ 500 ms（对比前沿 LLM 的 3 ~ 329 秒） |
| 输入价格 | $0.042 / 百万 token |
| 输出价格 | **免费**（官方称低到无法计量） |
| 相对提速 | 40 ~ 200 倍（自报） |
| 相对降本 | 40 ~ 400 倍（自报） |
| 四工作流基准准确率 | 约 68%（**自设基准，无独立验证**） |

### 2.5 能力边界（必须正视）

1. **不能生成文本**——不能写总结、不能解释理由、不提供 chain-of-thought。
2. **"零幻觉"是有限承诺**——官方所述零幻觉实为**零类型错误**：它不会编造选项之外的答案，但**仍可能把 A 选成 B**，即"类型正确而事实不一定正确"。
3. **置信度经 RLCD 训练校准**——官方称被标为 0.9 的结果真实发生率约 90%。**这是本项目 T2 阈值能真正生效的前提**，也是相较普通 LLM 最实质的优势。
4. **state 中混入无关内容会显著降低准确率**——官方文档明确提及。
5. **官方 API 尚未向中国大陆开放**（央广网 2026-09-20 报道原文），且服务在境外。
6. **服务稳定性**——发布初期出现基础设施过载，公开报道提及开发者集中接入导致服务承压。

### 2.6 开源替代方案

| 方案 | 说明 |
|---|---|
| **Nimble** | `bespokelabsai/nimble`，基于 Qwen3.5-9B 做 LoRA 微调，Apache 2.0 许可，**支持纯本地离线运行**（GPU 或 Mac/PC 均可）。与参考标签一致率 90.12%（Jev 为 93.21%） |
| fast-browser-use | APUS 出品，MIT 许可，面向浏览器自动化场景的 Jev 范式复现 |

## 三、决策结论

| # | 决策项 | 结论 | 依据 |
|---|---|---|---|
| 1 | 判定模型 | 采用 **Jev** 作为路由判定的执行体 | HD 指定需求 |
| 2 | 判定粒度 | **两级映射**：Jev 只判 `task_type` 与特征标记，具体 `model_id` 由代码层按映射表 + 成本/延迟权重决定 | Jev Choice 的候选必须**预先枚举**；若把模型池做成候选，则模型增删都要改判定配置，且候选越多准确率越低 |
| 3 | 路由层数 | 由四层简化为**三层**（L1 规则短路 → L2 Jev 判定 → L3 组合选型与兜底） | 原 L2 语义召回的存在价值是"省下 LLM 裁判的延迟与费用"，而 Jev 本身已足够快且便宜，再维护向量库 + 样本集 + 阈值调参投入产出不成正比 |
| 4 | 部署策略 | 先按 **Jev 官方 API** 实现，同时经 `BaseDecider` 抽象保留本地复现版（Nimble）/ 国内模型切换能力 | Jev 未对中国大陆开放，直接耦合厂商 SDK 会导致方案在合规或可达性变化时被迫返工 |

## 四、设计影响分析

### 4.1 正面影响：一大批防御性工程可以取消

| 原设计中的工程负担 | 变更后 | 原因 |
|---|---|---|
| 强制 JSON Schema / JSON mode 约束输出 | **取消** | Jev 非自回归，答案空间预先定义，类型层面不可能出错 |
| `temperature = 0` 保证稳定性 | **取消** | 不做自回归采样，`temperature` 概念不适用 |
| Pydantic 模型 `JudgeOutput` 二次解析校验 | **取消** | 无需解析文本，返回即结构化 |
| `JUDGE_PARSE_ERROR` 解析失败兜底分支 | **取消** | 上述兜底场景不再存在 |
| LLM 的 `confidence` 是"编的"、不可信 | **改为可用** | Jev 置信度经 RLCD 校准，T2 阈值从此有实际意义 |
| 判定延迟 200~800ms | **降为 70~500ms** | 官方标称区间 |
| few-shot 样例注入 prompt | **改为 `criteria` 描述** | Jev 通过选项描述（`what` / `not_for` / `examples`）而非样例来界定类别 |

### 4.2 新增的设计约束

| # | 约束 | 说明 |
|---|---|---|
| 1 | **`reason` 字段被移除** | Jev 不产出文字理由。可解释性改由 `probabilities` 概率分布承载，并辅以 `complexity` / `has_code` / `is_sensitive` 三个特征标记。**概率分布比 LLM 编造的理由更可信**，但它是数值而非句子 |
| 2 | **候选必须预先枚举** | 直接导致「二级映射」决策。`task_type` 枚举与 `task_type → 模型` 映射配置必须**单一来源定义**，否则会出现漂移（已列为风险 TR-017） |
| 3 | **`state` 必须保持干净** | 官方明确无关内容会降低准确率。送入 Jev 的文本应只包含待判定内容，不混入历史对话与系统提示 |
| 4 | **单次调用并行提问** | 四个问题必须一次调用完成，禁止拆成四次，也禁止串行 |
| 5 | **判定器必须抽象** | `BaseDecider` 是本方案应对"未对中国大陆开放"风险的关键保险，必须在 MVP 阶段落实，而非事后重构（已列为风险 TR-016） |
| 6 | **准确率不采信厂商标称值** | 厂商自报 68% 低于本项目 85% 验收线，且为自设基准。必须以自建 `eval_case` 评测集实测为准 |

### 4.3 保留不变的设计

- 对外 **OpenAI 兼容协议**入口（`POST /v1/chat/completions`，`model="auto"` 触发自动路由）
- **L1 规则短路**保留：能用确定性规则秒判的场景没必要付出一次网络往返
- **路由决策先于首个 token 下发**的硬约束
- **失败兜底率 100%**：任何异常都必须返回可用模型，不允许 5xx
- **判定结果幂等缓存**（输入 hash）
- **Adapter 层隔离**各厂商协议与流式格式差异
- 数据库 8 张表（其中 `route_sample` 重定义为 `decision_sample`）、控制台 9 个页面、技术栈主体

## 七、对后续阶段的约束

1. **阶段二**《架构设计文档》必须体现三层路由与 `BaseDecider` 抽象；《数据库设计》须按 `decision_sample` 表定义；《安全方案文档》须覆盖"判定请求出境"的数据合规说明。
2. **阶段二**的《接口设计说明书》中，`/admin/route/preview` 出参必须以 `probabilities` 与 `features` 替代 `reason`。
3. **阶段三**开发时，`BaseDecider` **至少要有两个实现**（Jev 官方版 + 本地/mock 版）并通过同一组契约测试，否则抽象形同虚设。
4. **阶段四**测试用例须覆盖：判定器超时、判定器返回结构非法、`task_type` 枚举外值、低置信兜底、合规拦截、候选集为空 —— **不再需要覆盖"非法 JSON 解析失败"这一类用例**。
5. **阶段四**的准确率评测必须以**自建评测集实测**为准，不得引用厂商标称的 68% 或任何自报数据作为通过依据。
6. **阶段二**《接口设计说明书》必须按基线 **3.1.1** 落地对外响应头约定（5 个 `x-router-*` 字段及各自取值时机），并说明流式场景下为何只能走 Header；**阶段五**《用户手册》须说明第三方如何读取这些字段自行排障。
