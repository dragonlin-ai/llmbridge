## 一、项目概述

### 1.1 项目背景

当前团队在多个业务场景中调用大模型，存在三个突出问题：

1. **模型选择靠人肉**：一个请求该走哪个模型，由开发者写死在代码里。想换模型就要改代码、发版，成本高、响应慢。
2. **接入成本重复**：每接一家厂商（OpenAI / Claude / 通义 / DeepSeek / 本地 vLLM）都要重写一套鉴权、重试、流式解析逻辑，协议差异反复处理。
3. **成本与效果不可见**：无法回答「上周调用花了多少钱」「简单问题是不是被贵的模型接走了」「路由到底准不准」这些问题。

同时，业务侧的真实诉求是：**用户丢一段文字进来，系统自己判断该用哪个模型**——代码问题给代码模型，长文摘要给长上下文模型，简单闲聊给便宜的快模型。这个判断不应该由业务方每次调用时手工指定。

因此需要一个独立的**大模型中转系统**，把「决策 + 转发 + 治理 + 观测」收拢到一层，对上提供统一接口，对下屏蔽厂商差异，并提供可视化控制台来配置与调优路由策略。

### 1.2 项目目标

- **目标一（核心）**：实现「输入一段文本 → 系统自动判定目标模型 → 完成转发」的完整闭环，路由判定准确率 ≥ 85%。
- **目标二（性能）**：路由决策带来的额外延迟 ≤ 800ms（P95），且必须在首个 token 下发之前完成。
- **目标三（健壮）**：任何路由异常（判定器超时、判定器返回结构非法、候选集为空、全部候选模型不可用）都必须兜底成功，失败兜底率 100%，不允许对外返回 5xx。
- **目标四（可控）**：提供可视化控制台，使「调整路由策略」从改代码发版变成点按钮配置，且每次判定都可追溯、可复盘。
- **目标五（统一）**：对外暴露 OpenAI 兼容协议，现有业务代码只需把 `base_url` 指过来即可接入，零改造。

### 1.3 项目范围

**包含范围**

- 统一接入层：OpenAI 兼容的 `/v1/chat/completions` 入口，支持非流式与 SSE 流式。
- 三层路由决策引擎：L1 规则短路 / L2 Jev 判定 / L3 组合选型与降级兜底。
- 执行层 Adapter 池：至少覆盖 OpenAI 协议、Anthropic 协议、OpenAI 兼容的本地 vLLM 三类适配器。
- 控制台 9 个页面：登录、概览、模型池管理、路由规则配置、路由试跑台、样本集管理、调用日志、评测看板、用量与成本。
- 可观测性：每次请求的完整 Trace（含命中层级、Jev 判定概率分布 `probabilities`、候选打分、降级原因）。
- 成本核算：基于模型单价表的请求级成本统计。

**不包含范围**

- 多租户隔离与账单体系（留待 V2.0）。
- 规则灰度发布与 A/B 实验框架（留待 V2.0）。
- 模型微调、模型托管、推理加速等能力。
- 面向 C 端的用户注册与自助充值。
- 复杂的企业级 RBAC 权限体系（MVP 仅区分管理员与只读两种角色）。

### 1.4 整体调用链路

![大模型中转系统整体调用链路](../assets/01-request-flow.svg)

一条请求的完整路径：

```
第三方系统 ──① POST /v1/chat/completions ──▶ 接入层
                                             │ 鉴权 / 限流 / 参数校验 / 协议归一
                                             ▼
                                          判定层
                                          ├─ Jev 判定  → task_type + confidence + probabilities
                                          └─ 映射表    → model_id
                                             │ 【决策到此必须结束，不得晚于首个 token】
                                             ▼
                                          执行层（Adapter 调用选中模型）
                                             │ 失败 → 按 model.priority 降级重试
                                             ▼
                                          下游模型池
                                             │
第三方系统 ◀──② 结果 + 判定元信息（响应头）── 中转封装返回
```

**链路三段的关键约束**

| 环节 | 关键约束 |
|---|---|
| 接入层 | 不合规请求在此拦截，不进入路由；协议差异在入口统一吸收 |
| 判定层 | **必须在下游调用之前完成**；判定结果（含 `probabilities`）必须落库 |
| 执行层 | 兜底率 100%，任何上游异常都不得对第三方透出 5xx |

**判定前置的必然性**：路由决策与下游生成是**串行**关系——不先知道调谁，就无法发起请求。所以本系统必然存在一层额外延迟（Jev 70~500ms），这正是 3.1 节「路由决策额外延迟 ≤ 800ms（P95）」这项指标的由来。流式场景同理：首个 token 下发前路由必须已定死，**不允许先返回再改道**，否则第三方会收到两个模型拼接的回答。

**返回给第三方的元信息**（走响应头，流式下 body 无法附加字段）：

| 响应头 | 含义 | 取值时机 |
|---|---|---|
| `x-router-model` | 本次实际调用的模型 | 始终返回 |
| `x-router-layer` | 判定命中的层级（`L1` / `L2` / `L3`） | 始终返回 |
| `x-router-task-type` | Jev 判定出的任务类别 | 仅 L2 命中时返回；L1 规则短路不经 Jev，无此项 |
| `x-router-confidence` | 判定置信度（Jev 校准值；L1 命中恒为 `1.0`） | 始终返回 |
| `x-router-trace-id` | 全链路追踪 ID | 始终返回 |

> **`x-router-layer` 不可省**：L1 规则命中时 Jev 根本未被调用，此时 `task-type` 与 `confidence` 反映不了真实判定过程，只有层级字段能说明「这次是规则秒判的」。缺失它会让线上排障时把规则命中的请求误读为 Jev 判定结果。

**责任边界**：第三方按本系统计价并直接向本系统报障；上游厂商的限流、涨价、协议变更均由本系统消化。这决定了降级与兜底必须是**内部静默**的。

### 2.3 功能描述

#### F-001 统一路由转发入口

**功能编号**：F-001
**功能路径**：接入与转发 → 统一接口 → OpenAI 兼容入口
**优先级**：高

**功能描述**：系统对外的唯一请求入口。接收 OpenAI 兼容格式的对话请求，当 `model` 字段传 `"auto"` 时触发自动路由；传入具体模型名时直接使用该模型（跳过路由判定，二者都仍走 Adapter 转发与观测链路）。

**输入**：
- HTTP `POST /v1/chat/completions`
- `messages`：对话消息数组（必填）
- `model`：模型名或 `"auto"`（必填，默认 `"auto"`）
- `stream`：是否流式（可选，默认 `false`）
- `temperature` / `max_tokens` 等透传参数（可选）
- Header `Authorization: Bearer <API_KEY>`

**输出**：
- OpenAI 兼容的响应体（含 `choices`、`usage`）
- 响应 Header 附带 5 个路由元信息字段：`x-router-model`、`x-router-layer`、`x-router-task-type`、`x-router-confidence`、`x-router-trace-id`（取值时机详见 1.4 节）

**业务规则**：
- `model` 为具体模型名时不做路由判定，直接转发；该模型不存在或已禁用则按 F-009 降级。
- `messages` 为空或整体 token 估算超过 `MAX_INPUT_TOKENS` 时，超出部分截断并记录截断事件。
- 请求必须携带合法 API Key，否则返回 401。
- 任何内部异常都必须被捕获并转为可用结果（见 F-009），不允许向调用方返回 5xx。

---

#### F-003 SSE 流式透传

**功能编号**：F-003
**功能路径**：接入与转发 → 统一接口 → 流式（SSE）响应
**优先级**：高

**功能描述**：以 Server-Sent Events 方式逐 token 下发上游模型的输出。

**输入**：
- 同 F-001，且 `stream = true`

**输出**：
- `text/event-stream` 响应流，每个分片为 `data: {...}\n\n`，结束为 `data: [DONE]\n\n`

**业务规则**：
- **路由决策必须在首个 token 下发之前完成**。不允许先返回占位内容再改道。
- 上游中断时，必须向下游发送结束标记并释放上游连接，不允许悬挂。
- 流式场景下 `usage` 若上游未返回，则由本地 token 估算补全后落库。

---

#### F-006 规则短路路由（L1）

**功能编号**：F-006
**功能路径**：智能路由 → L1 规则短路
**优先级**：高

**功能描述**：用成本近乎为零的确定性规则拦截一部分请求，避免为它们付出 LLM 判定的延迟与费用。

**输入**：
- `input_text`、`token_len`、`session_id`、`tenant_id`

**输出**：
- 命中时返回 `RouterDecision(hit_layer="L1", model_id=..., matched_rule_id=..., confidence=1.0)`，并附带 `explain` 说明命中的规则名
- 未命中时返回 `None`，交由 L2（Jev 判定）处理

**业务规则**：
- 规则类型支持：关键词包含、正则匹配、token 长度阈值、租户白名单、会话显式指定。
- 多条规则同时命中时，按 `route_rule.priority` 升序取第一条（数值越小优先级越高）。
- 被禁用的规则（`enabled = false`）不参与匹配。
- L1 命中即为终态，不再进入 L2（Jev 判定）与 L3（组合兜底），`confidence` 固定为 1.0。

---

#### F-007 判定器可插拔（BaseDecider）

**功能编号**：F-007
**功能路径**：智能路由 → 判定器抽象
**优先级**：高

**功能描述**：路由层不直接依赖 Jev 厂商 SDK，而是面向统一的判定器接口编程。系统先实现 Jev 官方 API 版本，同时保留本地复现版（Nimble，基于 Qwen3.5-9B LoRA）与国内模型实现位，以便按部署环境与合规要求整体切换判定引擎，而无需改动路由链路代码。

**输入**：
- `state`（用户输入文本）
- `questions`（提问定义：问题 id → Choice / Score / Noul 定义）

**输出**：
- 统一的 `DeciderResult`：`answers`（问题 id → 判定结果）、`latency_ms`、`raw_usage`

**业务规则**：
- 所有判定器实现必须满足同一接口契约，并接受同一组提问定义。
- 切换判定器只允许通过配置项完成，不允许出现「因换判定器而改业务代码」。
- 判定器的连通性与响应延迟必须支持独立健康检查。
- **该能力是应对「Jev 官方 API 未对中国大陆开放」的关键保险**，MVP 阶段即须落实接口抽象，而非事后重构。

---

#### F-008 Jev 决策判定（L2）

**功能编号**：F-008
**功能路径**：智能路由 → L2 Jev 判定
**优先级**：高

**功能描述**：这是需求中「**先通过 Jev 判断该调用哪个大模型**」的直接实现。调用 TypeSafe AI 的 Jev（System One 决策模型）对输入做判定。Jev 不生成文本，而是对提交的**多个原子问题并行评估**，直接返回类型化结果与**校准概率**。

注意：**Jev 只判定 `task_type`（任务类别）与若干特征标记，不直接输出 `model_id`**。具体模型由 L3 组合层按映射表与权重决定（见 F-009）。原因是 Jev Choice 的候选必须预先枚举，若直接把模型池做成候选，则模型一有增删就要改判定配置，且候选越多准确率越低。

**输入**：
- `state`：用户输入文本（截断至约 2000 字符；**state 中不应混入与判定无关的内容**，官方明确说明无关内容会显著降低准确率）
- `questions`：固定四问
  - `task_type`（Choice）：候选项为预设任务类别枚举
  - `complexity`（Score）：`["简单", "中等", "复杂"]`
  - `has_code`（Noul）：输入是否包含代码块
  - `is_sensitive`（Noul）：是否涉及合规敏感内容

**输出**：Jev 原始响应中的 `answers`

```json
{
  "task_type": {
    "type": "choice",
    "choice": "code_generation",
    "confidence": 0.87,
    "probabilities": { "code_generation": 0.87, "reasoning": 0.09, "general_chat": 0.04 }
  },
  "complexity": { "type": "score", "score": 1.0, "confidence": 1.0, "probabilities": { "0": 0.0, "1": 1.0, "2": 0.0 } },
  "has_code": { "type": "noul", "noul": 1.0 },
  "is_sensitive": { "type": "noul", "noul": 0.0 }
}
```

**业务规则**：
- 四个问题在**一次调用**内并行评估，不得拆成四次调用，也不得串行等待。
- `task_type` 必须取自预设枚举，出现枚举外的值视为判定无效。
- `task_type.confidence` 低于 `ROUTE_CONFIDENCE_THRESHOLD_T2`（默认 0.5）时视为**低置信**，转入 L3 兜底。
- **`probabilities` 概率分布必须持久化写入 `request_log.router_output_json`**。这是本系统的可解释性来源，用于人工复盘与判定准确率调优。
- 因 Jev 为非自回归模型，输出为类型化结果，**不存在非法 JSON 或格式解析失败**，无需 JSON Schema 强制与二次解析校验。
- **不再使用 `temperature = 0`**：Jev 不做自回归采样，不存在采样随机性。
- 判定调用超时独立配置（建议 3s），超时即视为判定失败，转入 L3 兜底。
- Jev 官方 API：`POST https://api.typesafe.ai/v1/systemone`，Bearer 鉴权，模型名 `jev-latest`；官方 Python SDK 为 `typesafe-sdk`，经 F-007 的 `BaseDecider` 接入。

#### F-009 组合选型与降级兜底（L3）

**功能编号**：F-009
**功能路径**：智能路由 → L3 组合选型与降级
**优先级**：高

**功能描述**：把 Jev 的判定结果**翻译成具体的 `model_id`**，并保证系统「永远有可用结果」。

**输入**：
- L2 的 `task_type`、`complexity`、`has_code`、`is_sensitive` 判定结果
- `task_type → 候选模型集` 映射配置
- `model.enabled`、`model.priority`、`model.input_price` / `output_price`

**输出**：
- 可用的 `model_id`，以及 `fallback_reason`（若发生兜底）与选型依据 `explain`

**业务规则**：
- **映射选型**：按 `task_type` 取候选模型集；候选为空时回退到 `DEFAULT_MODEL_ID`。
- **加权排序**：候选集内按「成本 / 延迟 / 模型优先级」三者加权打分排序（权重可配置），取最高分。`complexity` 高时提升高质量模型权重；`has_code = true` 时可强行过滤掉无代码能力的模型。
- **合规拦截**：`is_sensitive = true` 时，过滤掉不允许承载敏感内容的模型，`fallback_reason = "SENSITIVE_BLOCKED"`。
- **低置信兜底**：Jev 判定无效或 `confidence < ROUTE_CONFIDENCE_THRESHOLD_T2` 时，改用 `DEFAULT_MODEL_ID`，`fallback_reason = "LOW_CONFIDENCE"`。
- **判定不可用兜底**：判定器超时、网络异常、返回结构不合法时，改用默认模型，`fallback_reason = "DECIDER_UNAVAILABLE"`。
- **模型不可用降级**：判定出的模型调用返回 429 / 超时 / 5xx 时，按 `model.priority` 升序尝试下一个可用模型，`fallback_reason = "UPSTREAM_UNAVAILABLE:<原始模型>"`。
- **兜底率必须为 100%**：构造任意异常输入（含判定器宕机、候选集为空、全部候选模型宕机）都必须返回可用模型，不允许出现 5xx 或空结果。
- 每一次兜底与降级都必须写入 Trace。

#### F-016 路由试跑

**功能编号**：F-016
**功能路径**：路由试跑调试 → 试跑执行
**优先级**：高

**功能描述**：控制台的核心调试抓手。输入一段文本，只执行路由判定链路并返回决策细节，**不真实调用下游模型**，因此零成本、可反复试。

**输入**：
- `{"text": "待判定的文本", "session_id": "可选"}`

**输出**：
- `hit_layer`：命中的层级（L1 / L2 / L3）
- `task_type`、`selected_model`、`confidence`
- `probabilities`：Jev 输出的完整概率分布（各 `task_type` 概率）
- `features`：`complexity` / `has_code` / `is_sensitive` 的判定值
- `candidates`：候选模型数组，每项含 `model_id` / `score` / `matched_rule`
- `latency_ms`、`trace_id`

**业务规则**：
- 试跑请求不写入 `request_log` 主表，单独记录到调试日志，避免污染用量与成本统计。
- 试跑必须返回**完整链路信息**，包括未命中层级的跳过原因，便于定位判定为何不符合预期。
- 试跑结果必须包含判定器实际耗时（`decider_latency_ms`），用于评估是否逼近延迟上限。

#### F-017 判定链路可视化

**功能编号**：F-017
**功能路径**：路由试跑调试 → 判定链路可视化
**优先级**：高

**功能描述**：以「链路条」形式直观展示 L1 → L2 → L3 的执行过程，标出在哪一层命中并终止，其余层标记为「跳过」。

**输入**：
- F-016 返回的完整链路数据

**输出**：
- 可视化的链路条 + Jev 概率分布图 + 候选模型打分行

**业务规则**：
- 必须显示**未命中层级的跳过原因**（例如「L1 未命中：无匹配规则」），这是排查问题的关键信息。
- 命中层级须有明确的视觉强调。
- Jev 的 **`probabilities` 概率分布必须完整展示**（各任务类别概率 + `confidence`），它替代原设计的 `reason` 原文成为可解释性来源；须支持复制。
- 候选模型列表须展示每个候选的**落选原因**（如成本更高、能力不匹配、被合规拦截），便于解释为何没选它。

## 三、非功能需求

### 3.1 性能需求

| 指标 | 要求 | 说明 |
|------|------|------|
| 路由决策额外延迟 | ≤ 800ms（P95） | 相对不做路由的直接转发，新增的判定期耗时 |
| L1 规则短路额外延迟 | ~0ms | 纯本地计算 |
| L2 Jev 判定额外延迟 | 70~500ms | 官方标称端到端响应区间；并行提问不显著增加耗时 |
| L3 组合选型额外延迟 | ~0ms | 纯本地映射与权重计算 |
| 控制台页面加载 | < 2s | 首屏 |
| 控制台接口响应 | < 500ms | 不含大表全量导出 |
| 并发能力 | ≥ 50 QPS | MVP 目标，可水平扩展 |

### 3.2 安全需求

- **认证方式**：对外 API 使用 `Authorization: Bearer <API_KEY>`；控制台使用 JWT。
- **授权机制**：控制台 MVP 区分「管理员」与「只读」两种角色。
- **密钥保护**：各厂商 API Key 以 AES-256-GCM 加密后落库，主密钥经环境变量注入、严禁入版本库；控制台只回显掩码（如 `sk-****abcd`）。
- **数据脱敏**：`input_text` 落库前按长度截断（默认 2000 字符），并支持配置敏感词替换。
- **SSRF 防护**：厂商 `base_url` 必须经白名单校验，禁止指向内网网段。
- **日志安全**：任何路径下 API Key 不得出现在日志中。
- **传输加密**：生产环境全链路 HTTPS。

### 3.3 可用性需求

- 系统可用性目标：99.5%（MVP 阶段）。
- **上游降级不影响自身可用性**：Redis 不可用时自动降级为「不缓存」，而非整体不可用；单个厂商不可用时自动降级到其他模型。
- 界面风格：简洁专业的技术控制台，信息密度偏高，操作路径短。

### 3.4 兼容性需求

- 浏览器：Chrome ≥ 110、Edge ≥ 110、Firefox ≥ 110（Safari 尽力支持）。
- 操作系统：开发环境 Windows，生产环境 Linux。
- 接口兼容：对外 `POST /v1/chat/completions` 与 OpenAI 官方接口保持字段兼容，现有 OpenAI SDK 客户端仅需修改 `base_url` 与 `api_key`。

### 5.1 功能验收标准

| 编号 | 验收项 | 验收条件 |
|------|--------|---------|
| A-01 | 自动路由闭环 | 调用 `/v1/chat/completions` 且 `model="auto"`，能自动判定并返回结果，响应头含 `x-router-layer` |
| A-02 | L1 规则短路 | 配置关键词规则后，含该关键词的输入命中 L1，且响应延迟增量 < 10ms |

| A-05 | 判定稳定性 | 同一输入连续调用 5 次，`task_type.choice` 完全一致 |

| A-09 | 模型池管理 | 新增接入点、做连通性测试、开关模型均可生效且即时反映到路由候选集 |
| A-10 | 密钥不回显 | 控制台与接口响应中，厂商 API Key 始终为掩码形式 |

流程：*配置模型池 → 配置路由规则 → 试跑验证 → 正式调用*

验收标准：
- 从零开始到完成一个可用的自动路由链路，全程通过控制台完成，无需改代码、无需重启服务。
- 路由规则保存后立即生效（下一请求即生效）。

## 六、附录

### 6.1 术语表

| 术语 | 说明 |
|------|------|
| L1 规则短路 | 路由决策第一层，用关键词 / 正则等确定性规则直接命中目标模型 |
| L2 Jev 判定 | 路由决策第二层，调用 Jev 决策模型判定任务类别与特征标记 |
| L3 组合选型与兜底 | 路由决策第三层，按映射表与权重把 `task_type` 翻译成 `model_id`，并处理低置信 / 判定不可用 / 模型不可用 |
| Jev | TypeSafe AI 的 System One 决策模型。不生成文本，只输出带校准概率的类型化判定 |
| System One 模型 | 面向「快速判断」而非「长文推理」的模型类别，命名取自卡尼曼的快慢思考理论 |
| Choice / Score / Noul | Jev 的三种提问原语：从选项中选一 / 按 rubric 打分 / 是非判断 |
| BaseDecider | 判定器抽象接口，屏蔽 Jev 官方版与本地复现版（Nimble）差异，支持配置切换 |
| 判定模型 | 执行路由判定的模型，本项目中即为 Jev |
| 兜底 | 判定失败时改用默认模型，保证系统永远有可用结果 |
| 降级 | 目标模型不可用时按优先级切换到备选模型 |
| trace_id | 单次请求的全链路追踪标识 |
| T2 | Jev 置信度阈值，`confidence < T2` 触发兜底 |
| Adapter | 执行层中屏蔽单个厂商协议差异的适配器 |
| auto | 请求 `model` 字段的保留值，表示触发自动路由 |
