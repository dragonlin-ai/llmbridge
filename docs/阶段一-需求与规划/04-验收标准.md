## 一、功能验收标准

### 1.1 核心功能

| 功能点 | 验收条件 | 优先级 |
|--------|---------|--------|
| 自动路由闭环 | 调用 `POST /v1/chat/completions` 且 `model="auto"`，能自动判定并返回结果；响应头始终含 `x-router-layer`、`x-router-model`、`x-router-confidence`、`x-router-trace-id`，L2 命中时另含 `x-router-task-type` | 高 |
| L1 规则短路 | 配置关键词规则后，含该关键词的输入 `hit_layer` 为 `L1`，且路由新增延迟 < 10ms | 高 |
| L2 Jev 判定 | 输入代码类文本 → `task_type = code_generation`；输入翻译类文本 → `task_type = translation`；同一输入连续 5 次调用 `choice` 完全一致 | 高 |
| L2 判定契约 | Jev 返回结构中 `task_type` 必在预设枚举内、`confidence` 为 0~1 浮点数、`probabilities` 各概率之和为 1；结构不符合契约时判为无效并走 L3 兜底 | 高 |
| L2 单次调用并行提问 | 一次请求返回全部 4 个问题的答案；链路记录中该次判定仅产生 1 次判定器调用 | 高 |
| L3 组合选型 | 按 `task_type` 取候选集并按权重排序命中最高分模型；`has_code = true` 时无代码能力的模型被过滤；`is_sensitive = true` 时触发合规拦截 | 高 |
| L3 兜底 — 低置信 | `confidence < T2` 时改用 `DEFAULT_MODEL_ID`，`fallback_reason = "LOW_CONFIDENCE"` | 高 |
| L3 兜底 — 判定不可用 | 判定器超时 / 网络异常 / 返回结构非法时改用默认模型，`fallback_reason = "DECIDER_UNAVAILABLE"` | 高 |
| L3 兜底 — 兜底率 | 构造 20 组异常输入（判定器超时 / 判定器返回结构非法 / 候选集为空 / 目标模型 429 / 目标模型 5xx / 全部候选模型禁用），**100% 返回可用结果，无 5xx、无空响应** | 高 |
| 模型降级 | 首选模型返回 429 或超时时，按 `model.priority` 降级到备选模型，`fallback_reason` 记录原始模型 | 高 |
| 判定可追溯 | `request_log.router_output_json` 中完整保存 Jev 的 `probabilities` 分布与特征标记；控制台 Trace 可完整展示并可复制 | 高 |
| SSE 流式 | `stream=true` 时分片顺序正确、以 `data: [DONE]` 结束；路由在首个 token 下发前已完成（首 token 时间 ≥ 路由延迟） | 高 |
| 路由试跑 | `POST /admin/route/preview` 出参含 `hit_layer` / `task_type` / `selected_model` / `confidence` / `probabilities` / `features` / `candidates` / `latency_ms` / `trace_id`；且试跑不产生真实上游调用 | 高 |
| 试跑链路可视化 | 试跑台展示链路条，命中层级高亮，**未命中层级显示跳过原因** | 高 |
| 模型池管理 | 新增接入点 → 连通性测试 → 新增模型 → 启用，全流程生效；启用后该模型出现在路由候选集 | 高 |
| 密钥加密与掩码 | 厂商 API Key 落库为密文；控制台与接口响应中始终为掩码（如 `sk-****abcd`），无任何导出明文入口 | 高 |
| 规则配置生效 | 新增 / 修改 / 禁用规则后，下一请求即生效，无需重启服务 | 高 |
| 规则优先级 | 多条规则同时命中时，按 `priority` 升序取第一条；拖拽调整后生效 | 高 |
| 判定缓存 | 同一输入连续请求，第二次命中缓存且路由延迟显著低于首次 | 中 |
| Trace 全链路 | 按 `trace_id` 可查出：命中层级、Jev 概率分布、候选打分与落选原因、降级原因、各阶段耗时 | 高 |
| 调用日志查询 | 支持按时间范围 / 模型 / 命中层级 / 是否兜底 / 关键词筛选，分页正确 | 高 |
| 控制台登录鉴权 | 未登录访问任意页面跳转登录页；Token 过期后自动登出 | 高 |
| 用量与成本统计 | 按模型与时间维度聚合的调用次数、tokens、成本均与 `request_log` 汇总一致（误差 < 1%） | 中 |

### 1.2 用户操作流程

**流程一：从零配置一条可用路由链路**

验收标准：
- 全程通过控制台完成，**无需改代码、无需重启服务**。
- 从「新增接入点」到「试跑验证通过」不超过 10 分钟。

测试方法：
1. 管理员登录控制台
2. 新增 1 个厂商接入点，填入 base_url 与 API Key，点击连通性测试 → 状态灯变绿
3. 新增 2 个模型（一个代码模型、一个通用模型），填入能力标签与单价，均启用
4. 新增 1 条 L1 关键词规则，关键词设为 ```python```，目标模型为代码模型
5. 进入路由试跑台，输入含 ```python``` 的文本 → 断言 `hit_layer = L1`、`selected_model = 代码模型`
6. 输入不含关键词的普通文本 → 断言 `hit_layer = L2`、`probabilities` 非空且 `task_type` 在枚举内
7. 用 curl 调用 `/v1/chat/completions`（`model="auto"`）分别发送上述两类文本，断言响应头 `x-router-layer` 与试跑结果一致

**流程二：排查一次兜底请求**

验收标准：
- 3 步内定位到兜底原因。

测试方法：
1. 进入调用日志，筛选「是否兜底 = 是」
2. 点击任意一条，右侧滑出 Trace 抽屉
3. 时间轴 L3 节点展示 `fallback_reason`，且能据此判断根因类型

**流程三：流式请求验证**

验收标准：
- 首个 token 返回时间 > 0 且路由元信息在首个 token 之前已确定。

测试方法：
1. `curl -N` 调用 `/v1/chat/completions` 且 `stream=true`
2. 观察分片按序到达，最后一片为 `[DONE]`
3. 检查日志中该 `trace_id` 的 `route_latency_ms` 早于首 token 时间

## 二、性能验收标准

### 2.1 响应时间

| 操作 | 响应时间要求 | 优先级 |
|------|-------------|--------|
| 路由决策额外延迟（含 L2 Jev 判定） | ≤ 800ms（P95） | 高 |
| 路由决策额外延迟（L1 命中） | ≤ 10ms | 高 |
| 路由决策额外延迟（L3 组合选型） | ≤ 10ms | 中 |
| 路由试跑接口（含 L2 Jev 判定） | ≤ 1s | 高 |
| 控制台页面首屏加载 | < 2s | 中 |
| 控制台列表接口 | < 500ms | 中 |

### 2.2 准确率与可靠性

| 指标 | 目标值 | 测量方法 |
|------|--------|---------|
| 路由判定准确率 | ≥ 85% | 用 50 条标注好的测试输入跑批，比对 `selected_model` 与期望 |
| 失败兜底率 | 100% | 构造 20 组异常输入，统计返回可用结果的比例 |
| 判定稳定性 | 5/5 一致 | 同一输入连续调用 5 次，`task_type.choice` 完全一致 |
| 成本统计准确率 | 误差 < 1% | 本地成本汇总与上游厂商账单比对 |

### 2.3 并发性能

- 支持并发请求 ≥ 50 QPS，连续压测 5 分钟无响应超时。
- 压测期间路由决策 P95 延迟不劣化超过 20%。
- 压测期间兜底率不高于 1%（正常输入场景）。
