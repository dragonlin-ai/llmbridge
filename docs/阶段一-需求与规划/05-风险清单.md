## 一、风险评估方法

### 1.1 风险等级定义

| 影响程度 | 严重程度 | 发生概率 | 风险等级 |
|---------|---------|---------|---------|
| 极高 | 灾难性（项目无法交付 / 线上不可用） | 极高 | 红色（高风险） |
| 高 | 严重（核心指标不达标 / 需要返工） | 高 | 红色（高风险） |
| 中 | 中等（部分功能降级 / 进度延后） | 中 | 黄色（中风险） |
| 低 | 轻微（体验瑕疵 / 可后置） | 低 | 绿色（低风险） |

### 1.2 风险响应策略

- **规避**：消除风险源，改变项目计划（如 MVP 缩减范围）
- **转移**：将风险转移给第三方（如依赖厂商 SLA）
- **减轻**：降低风险发生概率或影响（如加缓存、加兜底）
- **接受**：主动接受风险，制定应急预案

## 五、风险监控

### 5.1 风险审查

- **审查频率**：每周一次（阶段三起提高为每两日一次）
- **审查人**：HD（齐活林）
- **审查内容**：
  - 风险状态更新（`已识别` → `已缓解` → `已关闭`）
  - 新增风险识别
  - 应对措施有效性评估
  - 红色风险逐条过，黄色风险抽查

### 5.2 风险等级重点关注

**当前红色风险（需 HD 直接跟进）：TR-001、TR-002、TR-004、TR-007、TR-009、TR-010、TR-016、TR-018、SR-001、SR-005、QR-001**

其中四条最需要前置动作：

1. **TR-007（Jev 可达性与合规）**：这是唯一可能让整体方案推倒重来的风险——官方 API 未对中国大陆开放且属境外服务。**必须在阶段二开工前完成两件事**：向 HD 确认业务是否接受输入文本出境；验证本地复现版 Nimble 的判定质量。这个结论越晚出，返工代价越大。
2. **TR-001（准确率）+ TR-002（延迟）**：这两条是 MVP 的核心验收指标，且互相拉扯（提高准确率往往要更复杂的判定 → 更高延迟）。Jev 的厂商标称准确率仅 **68%**，**必须以自建评测集实测为准**。建议在阶段三第 1 周就搭好评测集与压测脚本，把指标测量前移，不要等到阶段四才发现不达标。
3. **TR-004（协议碎片化）**：影响面最广但最容易被低估。建议 MVP 阶段**只做 OpenAI 兼容协议的完整支持**，Anthropic 与 vLLM 若为 OpenAI 兼容实现则复用同一 Adapter，真正需要独立适配的厂商降到最低。
4. **SR-001（前端工期）**：这是最容易导致整体延期的单点。P1/P2 页面后置的决策要尽早做，不要等到第 3 周才砍。
