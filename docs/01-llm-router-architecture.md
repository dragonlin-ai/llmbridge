## 一、需求本质

先把原始需求翻译成工程语言：

> "根据一段输入文字，先由一个大模型判断这段内容该调用哪个大模型。"

拆开是三个能力，缺一不可：

| # | 能力 | 说明 | 最容易被忽略的点 |
|---|---|---|---|
| 1 | **判定** | 对输入做意图/任务分类，得出"该用哪个模型" | 判定本身必须**快且便宜**，不能用贵模型来做路由 |
| 2 | **转发** | 按判定结果把请求发到目标厂商，结果（含流式）原样回传 | 各家协议、参数名、stream 格式都不同，必须有适配层 |
| 3 | **配置与观测** | 可视化配置路由策略与模型池，并能复盘每次判定是否合理 | 没有 Trace 和评测集，路由规则永远调不准 |

**结论：这不是"两个 API 串起来"的小工具，本质是一个 LLM 网关 + 智能路由系统。**

## 二、路由决策设计（核心）

### 2.1 不要一上来就"让大模型判断"

纯 LLM 分类路由有三个天然问题：

- **延迟翻倍**：判定是一次 LLM 往返，串在真实调用之前
- **不确定性**：同一段文本两次判定可能给出不同答案
- **成本**：每次请求都多花一次推理费用

正确做法是**分层路由，越便宜的手段越靠前**：

| 层级 | 手段 | 经验命中率 | 额外延迟 | 成本 |
|---|---|---|---|---|
| L1 规则短路 | 关键词 / 正则 / 租户白名单 / 显式指定 | 20~40% | ~0ms | 0 |
| L2 语义召回 | embedding 与标注样本比对，top-1 相似度 ≥ 阈值即采用 | 30~50% | 20~60ms | 极低 |
| L3 LLM 裁判 | 小模型 + 结构化输出（JSON Schema） | 剩余全部 | 200~800ms | 低 |
| L4 校验兜底 | 低置信 / 解析失败 → 默认模型 | — | 0 | 0 |

L3 就是需求里说的那一步，但它应该是**兜底主力**，不是唯一手段。

### 2.2 L3 裁判模型怎么设计

- **选小不选大**：gpt-4o-mini / claude-haiku / qwen-turbo / 本地 3B~7B。裁判不需要聪明，需要稳定。
- **输入**：待判定文本（截断至 ~500 token）+ 候选标签枚举 + few-shot 样例（每个标签 2~3 条真实样本）。
- **输出必须结构化**，用 function calling 或 JSON mode 强约束：

```json
{
  "task_type": "code_generation",
  "model_id": "deepseek-coder",
  "confidence": 0.87,
  "reason": "输入包含 Python 代码与调试诉求"
}
```

  - `task_type` 只能是枚举值，不允许自由发挥
  - `model_id` 必须命中候选模型池，否则视为无效输出
  - `confidence` 用于后续阈值兜底
  - `reason` 写入 Trace，供人工复盘（这条字段不能省）

- **temperature = 0**，保证同一输入的判定结果稳定。
- **幂等缓存**：对输入做 hash（或对 embedding 做近邻），命中缓存直接返回。

### 2.3 判定维度不只是"任务类型"

生产环境里路由通常要同时权衡四个维度，建议一开始就设计成**可配置权重**，而不是写死：

| 维度 | 示例 |
|---|---|
| 任务类型 | 代码 / 翻译 / 长文摘要 / 数学推理 / 闲聊 / 结构化抽取 |
| 成本预算 | 便宜模型优先，或设置"单请求成本上限" |
| 延迟要求 | 实时对话走快模型，离线批处理走强模型 |
| 能力与合规 | 必须支持 function call / 必须长上下文 / 必须境内合规 |

### 2.4 默认策略（MVP 建议）

- 无法判定 → 走可配置的"默认模型"
- 判定命中模型不可用（超时 / 限流 / 欠费）→ 按优先级降级到备选模型，降级事件记入 Trace
- 所有判定结果都写日志，**必须含 reason**

## 三、系统架构分层

| 层 | 职责 | 关键点 |
|---|---|---|
| 接入层 | 对外统一 OpenAI 兼容接口 `POST /v1/chat/completions` | 鉴权、配额、SSE 流式透传。兼容 OpenAI 协议 = 现有客户端零改造接入 |
| 路由层 | 执行 L1~L4 决策，输出 model_id | 决策要可解释、可缓存、可灰度 |
| 执行层 | 适配各厂商协议，处理重试与降级 | **Adapter 模式**，每家一个 adapter，统一超时与重试策略 |
| 数据层 | 配置、日志、评测集、计费 | 配置存 DB + 本地缓存，支持热生效 |
| 控制台 | 可视化配置与观测 | 与后端解耦，纯 API 驱动 |

## 四、数据模型（最小集）

| 表 | 关键字段 | 说明 |
|---|---|---|
| `provider` | id, name, base_url, api_key(加密), enabled | 厂商 / 接入点 |
| `model` | id, provider_id, model_name, capabilities, input_price, output_price, enabled | 模型池，价格用于计费 |
| `route_rule` | id, priority, type(rule/semantic/llm), condition_json, target_model_id, enabled | 路由规则，热生效 |
| `route_sample` | id, text, embedding, task_type, model_id | 语义召回的标注样本集 |
| `prompt_template` | id, scene, content, version | 裁判 prompt 模板，可版本化回滚 |
| `request_log` | id, trace_id, input_text, router_output(json), final_model_id, latency_ms, tokens, cost, status | 核心可观测表 |
| `eval_case` | id, input_text, expected_model_id | 评测集，用于算路由准确率 |

## 五、后端接口（最小集）

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/v1/chat/completions` | 对外主入口，走完整路由链路 |
| POST | `/admin/route/preview` | **路由试跑**：只返回判定结果，不真正调用下游 |
| CRUD | `/admin/providers`、`/admin/models` | 模型池管理 |
| CRUD | `/admin/rules` | 路由规则管理 |
| CRUD | `/admin/samples` | 语义样本管理 |
| GET | `/admin/logs` | 调用日志查询 |
| GET | `/admin/stats` | 用量、成本、路由准确率看板 |

> `/admin/route/preview` 是**性价比最高的一个接口**——它把"调路由"从改代码变成点按钮。

## 六、前端控制台页面清单

| 页面 | 核心交互 | 优先级 |
|---|---|---|
| 概览 | 请求量 / 成本 / 路由命中分布 / 平均延迟 | P1 |
| 模型池管理 | 新增厂商接入点、测连通性、开关模型、配价格 | P0 |
| 路由规则配置 | 规则列表（拖拽调优先级）+ 条件编辑器 | P0 |
| **路由试跑台** | 输入一段文字 → 实时显示命中层级、判定理由、候选打分 | P0 |
| 样本集管理 | 上传标注样本、一键批量 embed、看标签分布 | P1 |
| 调用日志 | 按 trace_id 查全链路，看判定理由与实际模型 | P0 |
| 评测看板 | 用评测集跑批，输出路由准确率 + 混淆矩阵 | P1 |
| 用量与成本 | 按模型 / 租户 / 时间维度聚合 | P2 |

**技术栈建议**（结合 `llmbridge_python` 项目命名）：

- 后端：Python + FastAPI + httpx（异步）/ SQLAlchemy，SQLite 起步 → PostgreSQL，Redis 做缓存与配额
- 前端：Vue3 + Vite + TypeScript + Element Plus（或 React + Ant Design），图表用 ECharts
- 流式：SSE

## 七、关键工程难点

1. **延迟叠加** — 判定串行在下游调用之前，等于每次请求多一次 LLM 往返。对策：L1/L2 前置过滤 + L3 结果缓存 + 延迟敏感场景直接跳过 L3。
2. **判定不稳定** — 限制枚举、temperature=0、JSON Schema 强约束、失败必兜底。
3. **协议碎片化** — 各厂商 tool_call 格式、stream chunk 格式、参数名都不同。Adapter 层必须把差异完全隔离，上层只认统一内部结构。
4. **流式回传** — 路由决策必须在**首个 token 下发之前**完成，不能先返回再改道；SSE 要处理粘包与中断。
5. **可观测性** — 每次请求必须记录"为什么选了这个模型"。没有 reason 字段，路由就是黑盒，无从调优。
6. **计费口径** — 不同模型单价差异大，需要维护统一价格表，否则成本统计失真。
7. **密钥安全** — 各厂商 API Key 加密存储，控制台只显示掩码，绝不回显明文。

## 八、分阶段落地建议

### MVP（先跑通闭环）

- FastAPI 单服务 + SQLite
- 3~5 个下游模型（可先接 1~2 家商用 + 1 个本地 vLLM 验证）
- 只做 L1 规则 + L3 LLM 裁判 + 兜底
- 控制台：模型池管理 + 路由规则 + 路由试跑台 + 调用日志
- **验收标准**：给定 50 条测试输入，路由准确率 ≥ 85%，路由决策额外延迟 ≤ 800ms

### V2（可运营）

- 补齐 L2 语义召回（embedding + 向量库）
- 样本集管理与批量 embedding
- 评测看板、准确率与混淆矩阵
- 规则优先级 + 灰度 + A/B

### V3（可商业化）

- 多租户、配额计费、账单
- 成本优化策略（按预算选模型）
- 规则热更新 + 版本回滚

## 九、需要先拍板的 3 件事

1. **下游模型范围**：只接境外 API（OpenAI / Claude），还是也要接国内（通义 / DeepSeek / 豆包）和本地 vLLM？
2. **路由判据的复杂度**：只按"任务类型"判定，还是同时考虑成本 / 延迟 / 合规的多维权衡？
3. **部署形态**：内网私有化单机部署，还是多租户 SaaS？

这三件事直接决定数据表结构和 Adapter 层的写法，建议先定下来再动手。
