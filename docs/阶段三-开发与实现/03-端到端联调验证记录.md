### 1.1 网络环境注意

本机存在**系统 HTTP 代理**，直连 `127.0.0.1:8000` 会被代理拦截并返回 `502 Bad Gateway`。验证脚本必须显式绕过代理：

```python
opener = urllib.request.build_opener(urllib.request.ProxyHandler({}))
```

否则会把代理错误误判为后端故障。

## 二、验证方法与判定标准

对**真实监听的 HTTP 端口**（非 ASGI 内存直调）发起请求，逐项判定：

| # | 用例 | 判定标准 |
|---|---|---|
| 1 | 控制台登录 `POST /admin/auth/login` | 200 且返回 `access_token` |
| 2 | 路由试跑 `POST /admin/route/preview`（含代码的文本） | 200 且 `hit_layer == "L1"`，选中模型为规则目标模型 |
| 3 | 对外非流式 `POST /v1/chat/completions` | 状态码 ∈ {200, 502}，**且 5 个 `x-router-*` 头齐全** |
| 4 | 对外流式 `POST /v1/chat/completions`（`stream=true`） | 200 且 `Content-Type` 为 `text/event-stream` |
| 5 | 无鉴权调用 `/v1/chat/completions` | 401 |
| 6 | 调用日志 `GET /admin/logs` | 200 且 `total ≥ 1` |

**为什么第 3 项接受 502 仍算通过**：种子数据的厂商密钥是占位符（`ENC_PLACEHOLDER_*`），不是合法密文，因此上游必然不可用。该用例真正要验证的是**基线硬约束「兜底率 100%，不得透出 5xx 裸栈」之外的元信息契约**——即无论成功或失败，`x-router-*` 5 字段必须恒在。真实上游调用链路见第五章「未闭环项」。

## 三、验证结果

执行结果（原文照录）：

```
PASS login          status=200
PASS preview_L1     layer=L1 model=deepseek-coder
PASS v1_nonstream   status=502
                    x=[x-router-confidence, x-router-layer, x-router-model,
                       x-router-task-type, x-router-trace-id]
PASS v1_stream      status=200 ct=text/event-stream; charset=utf-8
PASS v1_unauthorized status=401
PASS logs           status=200 total=8
HTTP_E2E_ALL_PASS
```

**6/6 通过。** 关键判定点：

- **L1 规则真实命中**：`hit_layer=L1` 且模型为 `deepseek-coder`。证明规则查询、条件匹配、目标模型解析三段链路完整可用（此前的缺陷 D-03 曾导致 L1 永不命中，见第四章）。
- **5 个响应头在失败路径仍然齐全**：证明 `x-router-*` 注入不依赖调用成功，满足基线「恒返回」要求。
- **SSE 契约成立**：`text/event-stream`，说明流式响应头在首包前正确注入。

前端：`vite build` 构建成功（1702 个模块）。

### 4.1 值得记录的七个坑

1. **D-03 是本次最隐蔽的缺陷**：功能不报错、日志不告警，只是「规则配置形同虚设」。根因是 SQLAlchemy 2.x 中 `.mappings()` 返回的 `RowMapping` 在 `select(Entity)` 形态下以**实体名**为键，而非列名——它是一个"看起来对、静默错"的写法。**后续凡是用 `.mappings()` 的地方都要复核键名口径**，或直接统一改用 `.scalars().all()`。
2. **D-05/D-06/D-11 属同一类问题**：把可能失败的调用放在 `try` 之外、或在 `except` 里 `break`，等于把内部异常直接升级成对外 5xx、或提前放弃兜底，违背基线「兜底率 100%，不允许 500」。**所有依赖外部输入的解密/解析/网络调用都必须包在异常处理内，且失败要 `continue` 走降级，绝不能终止整条链**。
3. **D-10 是 id 空间混用**：`Model` 与 `Provider` 各有自己的主键，`providers[model.id]` 这种写法在 id 数值巧合相同时「碰巧能跑」，是典型的**偶发正确**陷阱。凡涉及两张表主键的字典查找，必须把键名（`provider_id` / `model_id`）写进变量名或注释。
4. **D-01 的外键顺序**：SQLite 默认开启外键约束，`add_all` 的提交顺序即插入顺序，被引用的行必须先落库。种子脚本、批处理导入脚本都要注意。
5. **D-12 是「引用检查不完整」**：删除操作只检查了**其中一张**引用表就放行，漏掉的引用在 DB 层炸成 500。教训有两条：① 凡是主键被多表引用的实体，删除前必须**枚举全部引用方**，而不是想起一张写一张——最稳妥的做法是用 `sys` / `metadata` 遍历全表外键，而非手工列举；② 引用不是一律禁止删除，要按**语义**分「配置类（阻止）」与「历史类（解绑保留）」，一刀切会让日志把配置管理锁死，一律放行则会让配置悬空。
6. **D-13/D-14 是「对接外部 API 只按字段名猜语义」的代价**：`complexity` 被当成整型类别、失败被 `return None` 静默吞掉——两者都**不报错、不告警**，一个把特征值算反、一个让故障隐身。教训：① 对接外部 API **必须用真实响应体逐字段校准类型与量纲**（本次靠 `score=1.64` 与 `legend` 才能推出 0~2 的期望值语义）；② 判定器这类「可失败但必须降级」的组件，**降级路径必须留可观测痕迹**，否则「降级成功」会掩盖「从未真正生效」。
7. **D-16 是 D-12 的「下一层」问题：保护措施必须配套解除路径**。分「配置类阻止 / 历史类解绑」是对的，但没问一句「被阻止的用户能不能自己解除」。`eval_case` 没有管理入口，于是「保护引用完整性」直接退化成「功能不可用」。**凡是给出「请先做 X」的报错，都必须验证 X 在现有 UI 里真的可做**；做不到时，要么补 X 的入口，要么在**明确告知后果**的前提下提供受控的强制路径（本次选了后者：可空外键解绑 + 二次确认，而 NOT NULL 的强引用仍硬阻止）。

### 4.8 路由试跑台：输出选中模型的真实调用结果

**需求**：「路由试跑台要输出最终选中模型的调用结果」。

**设计决策（两条硬约束，均在代码注释与本文档留痕）**

1. **默认不调用，开关显式开启**。原设计的核心价值是「零成本试跑」——只决策不产生费用，用于反复调规则/判定器。若改成默认调用，每次试跑都会烧 token。故新增 `execute` 开关（默认 `false`），开启后才真实调用并回带输出。
2. **执行模式不做降级**。降级是线上保护；试跑台的职责是如实暴露「这个模型到底通不通」。自动降级会让「选中模型不可用」被另一个模型的成功掩盖，诊断价值归零。因此失败直接返回错误分类，不做候选重试。
3. **两种模式都不落 `request_log`**。试跑属诊断流量，落库会污染线上成功率与成本口径（已在验证中确认）。

**接口变更**：`POST /admin/route/preview` 入参新增 `execute: bool = false` 与 `max_tokens`（默认 512，上限 4096）；响应新增 `execution` 字段（`null` 表示仅决策）。

### 4.10 「界面显示的模型 ≠ 真实调用的模型」定位与整改（D-18 / D-19 / D-20）

**用户报告**：*「日志中显示的大模型和真实调用的大模型不一致」*。这个描述有**两个各自独立的成因**，都真实存在，已分别定位并整改。

**成因一：试跑台的候选打分与真实决策不同源（D-18）**

实测同一屏（`ui-shots/22`）暴露矛盾：候选表第一行是 `qwen3.8-flash 75.0`，而选中/实际调用是 `deepseek-v4-flash`。

- 真实决策走 `pipeline.l3_pick`：能力 0.6 + 成本 0.25 + 延迟 0.15 加权，按 `(-score, priority)` 取首；
- 试跑台打分走另写公式 `prob × 0.75`：两个模型都无能力标签 → **分数完全相同**（都 75.0），排序退化成「谁在前面谁第一」；
- 于是「展示的排名」与「真实的挑选」各算各的。**两个模型都没有能力标签**（`capabilities=[]`）让这个偏差最大化——真实逻辑此时完全由成本决定，展示却没有任何成本因子。

|---|---|---|
| V1–V3 | 候选表首行 = 选中模型；`picked` 恰好一个且指向选中；分数严格降序（+实测 `0.7 / 0.575 / 0.45`） | **PASS** |
| V4–V5 | `selection_basis` 明示「没有任何模型声明该能力标签，退化为按成本排序」；每个候选都标注能力标签状态 | **PASS** |
| V7 / V9 | 实际调用模型 == 选中模型 == 候选表首行（试跑台不降级） | **PASS** |
| V12–V16 | 纯函数：无能力标签选最便宜 ✓；有能力标签者胜出（权重压过成本）✓；池外候选标 `in_pool=false` ✓；同分按 priority ✓ ——**首行恒等于 `l3_pick` 的结果** | **PASS** |

**成因二：日志的模型归属随模型删除一同丢失（D-19）**

`ui-shots/23` 里 20 条日志有 15 条「实际调用模型」为空——因为 `request_log` 只用外键记录模型，而删除模型时按设计必须把历史引用解绑（否则模型永远删不掉）。**代价是「这次到底调了谁」这个既成事实被抹掉**，看日志的人自然得出「日志显示的模型和真实调用的对不上」的结论。

## 六、结论

1. 后端**主链路（登录 → 规则命中 → 对外接口 → SSE → 鉴权 → 日志）在真实 HTTP 环境下 6/6 通过**，基线中的两条硬约束（`x-router-*` 元信息头恒返回、SSE 契约在首包前生效）得到实测支撑。口径澄清：恒定返回的是 4 项（trace-id / layer / model / confidence），第 5 项 `task-type` 仅 L2 命中时返回（接口设计说明书 §2.2）。
2. **控制台各页面所依赖的接口 10/10 通过**，且全部经 vite 代理链路（浏览器同款路径）验证，前端接口路径与后端路由逐一对齐，无契约错配。
3. 累计发现并修复 **28 个缺陷**（P0×7 / P1×15 / P2×6）。其中 D-03、D-10、D-13 为「静默错」级（不报错、不告警，分别是 L1 规则空转、降级连错厂商、复杂度特征方向反），D-12 为「引用检查不完整」级（漏检的外键在 DB 层炸成裸 500），D-14 为「故障隐身」级（判定器失败被伪装成低置信降级），D-16 为「保护措施缺解除路径」级（引用保护本身正确，但被保护的引用方没有任何管理入口，于是删除功能整体不可用），**D-17 为「统计口径漏一半」级**（流式请求的 token/成本从未落库，而流式恰是对外主用法——非流式的正确掩盖了流式的缺失），**D-18 为「展示与决策各算各的」级**（试跑台候选打分另写一套公式，与真实挑选逻辑不同源，于是同一屏给出两个互相打架的结论），**D-19 为「事实随配置蒸发」级**（日志只存可变外键、不存事实快照，模型一删历史归属即消失，看日志的人自然认为「日志和真实调用不一致」），**D-21 为「启动像是好的、一用就死」级**（事件循环与数据库驱动不兼容，服务正常启动且 `/health` 返回 200，唯独任何数据库访问都 500），**D-22 为「环境判断绑错变量」级**（把「是否开发环境」耦合到数据库类型上，换库即静默反转，功能失灵但报错文案指向别处），**D-24 为「自检自己误报」级**（用类名做等值比较判断事件循环类型，把正常情况报成错误——会误报的告警会训练人忽略告警），**D-25 为「预置即坏」级**（候选池不校验厂商是否已接入，批量预置厂商后，未填 Key 的厂商其模型仍会被选中并必然失败，对外表现为随机 502——「只有零星手工厂商」掩盖了这条路径的缺失），**D-27 为「看不见的截断」级**（列表接口默认分页 20，超出部分静默消失，界面上没有任何异常迹象，只能靠比对库中行数与渲染行数发现）。这类问题的共同特征是**症状与根因距离远**，只能靠断言真实行为、逐条枚举引用方、逐字段核对外部 API 真实响应、**把落库字段一并断言**，以及**让展示层复用决策层的同一份计算**来定位与预防。
4. **前端具备可构建产物**，10 个控制台页面与路由菜单齐备，dev 服务器可启动并正常代理到后端。
5. **Jev 判定器已从 mock 切换为真实调用并实测通过**（§4.4，53/53）：5 类输入全部命中 L2 且 `decider=jev`，任务类型判定 5/5 正确；这同时**推翻了 K-01 的预判**（「Jev 国内不可达」不成立，本机直连 HTTP 200 可达）。注意：这验证的是**判定路径**，不等于上游生成链路已通（见 U-01）。
6. **端到端「真的通」已有证据，但阶段三门禁仍不得判定通过**：U-01 已闭环（§4.9）——真实厂商密钥下，非流式与流式均返回真实内容、5 个 `x-router-*` 头齐全、调用如实落库；此前该链路只有「失败降级」证据。**仍未过门禁的原因只剩一条**：门禁要求「单测覆盖率 ≥ 80%」，当前无数据（U-04）。

## 七、数据库由 SQLite 切换为 PostgreSQL（2026-09-22）

### 7.1 背景

代码与文档原本就声明「开发 SQLite → 生产 PostgreSQL」，但**实际从未切过**，根因藏在依赖里：

```
pyproject.toml: "asyncpg>=0.29; sys_platform != 'win32'"
```

该条件把 asyncpg 排除在 Windows 之外，而本机是 Windows → **等于把开发环境绑死在 SQLite 上**。
按用户指令本次切换为 PostgreSQL，并统一开发/生产驱动。目标实例：`47.99.134.147:5432`（PostgreSQL 17.10 / Debian），
新建独立库 `llmbridge`（该实例上已有 `contract_db`、`llmapp*` 等其他项目的库，不混用、不污染）。

### 7.5 本轮新增缺陷（均当场修复并复验）

| 编号 | 级别 | 症状 | 根因 | 处理 |
|---|---|---|---|---|
| **D-21** | P0 | 服务**正常启动**，但一访问数据库即 500（登录失败） | Windows 下 uvicorn 在「非子进程模式」返回 `ProactorEventLoop`（见 `uvicorn/loops/asyncio.py`），而 psycopg3 的异步实现**主动拒绝** Proactor：`InterfaceError: Psycopg cannot use the 'ProactorEventLoop' to run in async mode`。且 `Server.run()` 用 `asyncio_run(..., loop_factory=...)` 显式传入factory，**`set_event_loop_policy()` 无效** | 新增 `app/core/eventloop.py`，经 uvicorn 官方支持的 `--loop <module:attr>` 通道注入 `SelectorEventLoop`；启动命令同步更新（技术实现文档 §五、架构设计文档 §七） |
| **D-22** | P1 | 「是否允许厂商 base_url 指向 http/localhost」的开关会**静默反转** | 原判断写成 `database_url.startswith("sqlite")`，把「是否开发环境」耦合到数据库类型上；换 PG 后恒为 `False`，本地/内网厂商地址全部被 422 拒绝，报错文案指向「地址不合法」，与真实原因无关 | 抽出独立配置项 `ALLOW_LOCAL_BASE_URL`，`.env.example` 标注生产必须 `false` |
| **D-23** | P1 | 迁移脚本首跑即失败：`DatatypeMismatch: column "enabled" is of type boolean but expression is of type smallint` | SQLite 无原生 BOOLEAN/DATETIME：`enabled` 存为整数 0/1、时间列存为字符串。裸 `psycopg` **不做方言转换**（那是 SQLAlchemy 的职责），且 PG 不允许 smallint→boolean 的隐式赋值转换 | 迁移脚本改为**按目标库真实列类型动态转换**（查 `information_schema.columns`，boolean→`bool()`、timestamp 列→`datetime.fromisoformat()`），不硬编码类型映射 |
| **D-24** | P2 | 自检**误报**：正常启动（Selector 循环）时也打出 ERROR | 自检用类名等值比较 `loop_name != "SelectorEventLoop"`，而 Windows 上 `asyncio.SelectorEventLoop` 的**运行时类型是子类 `_WindowsSelectorEventLoop`** → 比较失败 | 改用 `isinstance(loop, asyncio.SelectorEventLoop)` 判层次，类名仅作兜底。**一个会误报的自检比没有自检更糟**——它会训练人忽略告警 |

> D-21 与 D-22 的共同点：**都不是「报错」，而是「静默走错」**。D-21 让服务看起来是好的（启动成功、`/health` 200），D-22 让功能看起来是坏的（报「地址不合法」）。两者都无法靠「接口返回 200」发现，只能靠断言真实行为与逐层核对配置生效值。

### 7.6 负向验证（证明自检不是摆设）

故意**不带** `--loop` 参数启动，观察自检是否命中：

```
INFO  event_loop=ProactorEventLoop psycopg_compatible=?     ← 实际打出 psycopg_compatible=False
ERROR Windows 下使用 PostgreSQL 必须跑 SelectorEventLoop（当前 ProactorEventLoop）…请带参数启动：--loop …
ERROR db connectivity=FAILED InterfaceError: (psycopg.InterfaceError) Psycopg cannot use the 'ProactorEventLoop'…
INFO  Application startup complete.
```

两条 ERROR 均命中，且**服务仍然启动完成**（刻意不中断启动，保持「可启动」与「故障显性」并存）。
这同时把 D-21 的症状从「运行时随机 500」提前到「启动即 ERROR」，降低后续排障成本。

### 7.7 未闭环 / 待确认

- **U-13（新增）**：目标 PG 为**公网实例**（`47.99.134.147`），连接延迟与稳定性未做量化（本次未测 P95、未做断网重连验证）。生产部署前建议改为内网/同区域访问，并核实是否启用 TLS（当前连接未指定 `sslmode`）。
- **U-14（新增）**：`postgres` 账号为**超级用户**且密码以明文存在于 `.env`（该文件已在 `.gitignore`，未入库）。按最小权限原则，建议为应用单独建库账号（仅授予目标库的 DML/DDL），并轮换当前密码。
- **U-15（新增）**：本次未验证 `/v1` 对外入口在 PG 下的完整成功路径（仅验证了 `/admin` 侧与控制台接口；`/v1` 依赖同一套 `db/session.py` 与 `request_log` 批量落库，风险低但未实测）。

### 8.5 本轮新增缺陷

| 编号 | 级别 | 来源 | 症状 | 根因 |
|---|---|---|---|---|
| **D-25** | **P0** | 既有 | 预置厂商后，未填 Key 的厂商其模型仍会被路由选中，然后必然失败降级，对外表现为**随机 502** | 候选池只按 `Model.enabled` 过滤，完全不看厂商是否可用。「只有零星手工厂商」时这个问题不显形，一旦批量预置就立即暴露 |
| D-26 | P1 | 本轮实现期引入，当场修复 | 预置的 27 个模型 `capabilities` 落库为 `{general,code_generation}`（PG 数组字面量）而非 JSON，下游 `json.loads` 必抛异常 | `capabilities` 列是 Text，直接传 Python `list` 会被 psycopg 适配成 PostgreSQL 数组类型。**必须显式 `json.dumps`** |
| D-27 | P1 | 既有 | 模型池有 30 个模型，界面只显示 20 个，后 10 个静默消失 | 列表接口默认 `page_size=20`，前端不传分页参数；且后端按 `priority` 排序，使用者真正在用的模型（`priority=100`）恰好被排在分页之外 |
| D-28 | P2 | 本轮实现期引入，当场修复 | 未接入模型报错为「模型已停用」，使用者去模型页找启用开关，启用后照样调不通 | 归因顺序错误。目录预置的模型同时满足「模型停用」与「厂商未接入」，必须先报后者——那才是唯一有效的下一步动作 |

**D-25 的修法**：新增 `services/provider_access.py` 作为「厂商是否已接入」的单一判据，
在 `load_routable_models()`（`/v1` 与试跑台共用的候选池加载入口）处过滤。
过滤放在入口而非调用点，是为了让两个入口自动一致——**「同一份决策内核」的前提是「同一份候选池」**。

**D-27 的两点观察**：这类缺陷的隐蔽性在于「界面上看不出少了东西」，只能靠**比对库中行数与渲染行数**发现；
本轮正是 CDP 脚本断言 `rowCount == 30`（当时得到 20）才暴露的。修法是前端显式传 `page_size`（`providers` 与 `models` 两处同源）。

### 8.6 未闭环 / 待确认

- **U-16（重要）**：目录中的 `input_price` / `output_price` 是 **2026-09 整理的参考价**，取自厂商官方定价页、官方发布会口径与第三方比价站快照。已知三类失真来源：**时间漂移**（国内大模型调价频繁）、**平台差异**（同一模型厂商直销与聚合平台价差可达 2~4 倍）、**计费口径差异**（缓存的命中/未命中、峰谷价、输入输出合并计价）。目录内已逐条标注口径，但**启用前必须按官网核对**。这不影响功能，直接影响 L3 成本因子与账单预估的准确性。

## 九、同一厂商的多接入方式：厂商分组多通道视图（2026-09-22）

> ⚠️ **本节的核心结论已被 §十 推翻，勿以此为准。**
> 本节基于 V1.5 的设计——`coding_plan`「照常登记、可填 Key、界面可见，**但不进候选池**」（见 9.2 与 9.3）。
> 2026-09-22 同日 HD 追加指令「**按套餐的也要加入路由，不要排除掉**」，V1.6 已将
> `ROUTABLE_ACCESS_KINDS` 扩为**全部五种形态**（含 `coding_plan` / `token_plan`）。
> 9.2 的三条依据（条款 / 协议 / 计费）**并未被否证，而是处置方式变了**：
> 由「系统硬挡」改为「系统如实告知 + 使用者自担风险」（条款原文落 `provider.terms_note`，
> 界面可展开警示，首次填 Key 时弹窗二次确认）。智谱 Coding「仅 Anthropic 协议」那条依据
> 经查官方文档**属实为误判**（官方明确同时支持两种协议），端点在 V1.6 中一并修正。
> 本节其余内容（9.1 需求、9.3 交付、9.4 验证、9.5 缺陷 D-29）作为**历史存档**保留，
> 但凡与 §十 冲突处，一律以 **§十 为准**。

### 9.1 需求原话

> 「一个厂家里面的，有多种方式，都给我接入到这个系统里面……有几种方式的接入都要放到记录里面、
> 厂家里面，然后在厂家里面，这个怎么样的一个表现形式，帮我想想办法，让用户操作起来就比较方便。」

### 9.2 结论先行：三者是**三套互不相通的体系**，不是三个档位

同一家厂商常同时卖几种产品，**密钥、端点、计费、限流全都不同，密钥彼此不通用**
（拿按量 API 的 Key 打订阅端点会返回 401）。因此「一条 `provider` 记录」的正确语义是
**一条接入通道**，而不是「一家厂商」。

| access_kind | 含义 | 密钥来源 | 计费 | 参与路由 |
|---|---|---|---|---|
| `api` | 按量 API | 开放平台 | 按 token 后付费 | ✅ |
| `package` | 预付费资源包 | **与 api 同 Key** | 先充值后抵扣 | ✅ |
| `batch` | 批处理 | **与 api 同 Key** | 按批优惠价 | ✅ |
| `coding_plan` | 编程订阅套餐 | 订阅页（专属 Key） | 包月积分 / 次数 | ❌ **（V1.5 口径，已被 §十 推翻 → V1.6 起为 ✅）** |
| `token_plan` | 通用 Token 订阅套餐 | 订阅页（专属 Key） | 包月 Token 额度 | ✅ **V1.6 新增** |

关于口径：「talking plan」按上下文理解为 **Token Plan（token 包 / 资源包）**，即上表的 `package`；
若指语音实时（Talk / Realtime）这类按分钟计费的产品，则属第四类，本轮未纳入。

> ⚠️ `package` / `batch` **刻意不单独建通道行**：它们不改端点、不改密钥、不改协议，
> 只是同一条按量 API 的**结算方式**。各建一行只会让使用者困惑「同一个 Key 该填哪一行」——
> 这是纯噪音。其价差已写在 `model.price_note`（如「低谷时段约 5 折」）。

> ⚠️ **【以下为 V1.5 结论，已被 §十 推翻】** `coding_plan` 照常登记、可填 Key、界面上可见，**但不进候选池**。
> 三个理由（依据均为厂商官方口径）：
> ① **条款**——Kimi 官方文档原文：「使用时请保持工具的真实身份标识，篡改客户端标识（User-Agent）
> 将被视为违规，可能导致会员权益暂停」，并写明「如需**在自己的产品中调用**大模型能力……请访问
> Kimi 开放平台」。本网关从上游看就是服务端中转，天然踩这条线。
> ② **协议**——智谱 Coding 端点只提供 Anthropic 协议，本项目仅实现了 OpenAI 兼容适配器。
> ③ **计费**——订阅制没有「元 / 百万 token」单价，硬填 0 会让它在 L3 成本因子上拿满分、长期霸占路由。
